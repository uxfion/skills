# Design principles

How the skills and instructions in this repo are designed, built, run and decided with the user. Read it before designing, changing, running or testing a skill, writing any document, or putting a design decision to the user. Ideas taken from mattpocock/skills (every skill read, 2026-10-29) are marked *(mattpocock)*.

**The document grows from the user's words.** When the user repeats a point or corrects a mistake and their words carry a design idea or a top-level principle, the agent, unprompted, restates their words in order, distills the core point in formal language at the place it belongs here, and asks whether to add it. On a yes, the principle goes into its section and the user's words, dated, into [design-principles-sources.md](design-principles-sources.md), which is only for checking where a principle came from or settling a doubt about it.

## 1. Who does what

A skill's work is split three ways, by what the work needs.

- **Scripts** do what is the same every time and certain: request, download, file, compare identifiers, record, wait, report. They are small, independent and cheap to run again — scaffolding.
- **Agents** do what differs from case to case, is uncertain or is new: a page a script cannot get past, a file it cannot judge, two records that may be one paper, a site behaving in a way not met before. An agent is autonomous and can be relied on: it looks (a page's elements through `opencli browser state` / `find`, a file's pages as images), explores and acts toward the goal. The jobs in the middle of a flow — searching, picking candidates, fixing keywords, asking when something is ambiguous, judging uncertain cases — are written as prompt, not code.
- **The user** does only what only they can: type a password, pass a CAPTCHA, make a decision. Every step on the way there, the clicks to a login page included, is the agent's.

### The boundary is the script's certainty

A script settles a case only when nothing is left to judge: the same bytes as a settled file, an identifier that matches, the host's own words stating the fact in text a script can read. Everywhere else it detects that it is unsure — its check fails or abstains, two independent methods disagree — stops, and hands the case over with its evidence. Doubt of any kind counts as unsure: a fact half-stated, a mark that may be an image, nothing stated. Recall beats precision: a doubtful case sent to an agent costs one look, a wrong case settled by a script costs the result. A rule a script applies is first tried on a few real cases.

A script past its boundary shows as a matcher deciding the uncertain branch: a regex, a keyword list, a similarity threshold, a special case per site, an auto-accept rule on top. A growing list of such rules is the signal to switch to detect-and-delegate: the matcher is removed, not extended. When a handoff was missed, the fix is the handoff, never another matcher or clicks coded into the script.

### Handoffs are part of the flow

Every passage of work between the three roles is designed, in both directions: a script stopping and an agent taking over, a main agent sending a subagent and the subagent reporting back, an agent asking the user and the answer coming back. What passes is a prompt (the brief), a handoff document (the record) or data (the files), and each is written for its taker: whom it goes to, the task, the requirements, the product, and every file or content needed, so the taker acts without guessing. A subagent's brief: §6.

**State lives in files** *(mattpocock: software-factory)*. Whoever starts a handoff, a script or an agent, puts its inputs where the taker reads them, and the answer comes back where the next step reads it: a record, a file, the command that writes it. Nothing a later step needs rests on the conversation's memory, so a run that stops and resumes finds the judgements already made instead of asking again.

**One writer per piece** *(mattpocock: to-tickets, writing-shape)*. Each file, and each block or field in it, has one writer: a script's blocks only that script writes, an answer enters only through the command that records it, and a taker reads its inputs without editing them.

At every point where a script stops, the SKILL.md says who takes over, with what brief, what comes back, and which script command records the answer; then the script resumes where it stopped. The flow carries the delegation, so the user never has to prompt for it. Who takes over:

- **One work item, one subagent**, where a skill fans out many items at once (a batch of papers). The subagent carries its item from the point where the script leaves it, in its own browser session (its own tab), through every remaining step: working pages, searching elsewhere, judging what it got, recording the answer. A later pass resumes the same subagent (Claude Code: `SendMessage`); where the harness cannot resume it, a fresh subagent gets the same brief file and the item's records, and reads what was already tried before it acts. It runs in the background on a cheap model (Claude Code `model: "sonnet"`, Codex `luna`), at most 5 at once, because bot checks can be strict.
- **Local judgements** that need no page — the label of a file already settled, the check of a parse — go to such subagents in batches, up to 10 at once, since they touch no site.
- **An agent that invokes a skill for its own task** — a server it needs, a deployment it was asked for — carries that task itself, handing only small judgements, such as reading a long log, to such a subagent.
- **Reading, research, synthesis and design** go to subagents on the session's own model.
- **What needs the user** is brought to the front, with an alert. In a run, the user's questions are gathered into one message at the run's pause, each with its evidence and the answers it takes, and the answer is recorded through the same command, by user; only what cannot wait, a gate or a password, alerts at once. Design decisions follow §5.

### Undecided never blocks the deliverable

What an agent cannot settle either is recorded as unknown, and the run goes on: a file that passed the paper check is kept even when its version is undecided (`Unknown-<Source>`), and listed for a later look. A taker that cannot finish says so *(mattpocock: diagnosing-bugs, wizard)*: what it tried, what it established, what is still needed, and who takes it next.

### Knowledge stays open

- **Schemes, vocabularies and lists** in a skill are starting points, and say so: the agent extends them for a new case (a tag, a venue, a dimension) and reports it, and what the user changes in conversation is the rule from then on. Each list, and each "only", is checked for whether it would stop an agent from doing the sensible new thing.
- **What sites, publishers and tools were seen to do** (where a publisher marks the version, which link holds the PDF) goes into references as dated hints the agent judges, never into recognition code: sites differ, pages of one site differ, markers change. The skill fixes definitions and vocabulary; recognising them is the agent's judgement, and where it is not confident, a background sonnet subagent looks.
- **What varies by machine** — where files go, which GPU, which build, how to recover a download — is principles plus dated hints for the calling agent, in the tool's own vocabulary (vLLM's arguments, not new keys); the script does only what is the same everywhere (start, stop, wait, report).

### Running a skill is following its flow

Every run, a test run included, follows the SKILL.md: at each stop, read the step for it and do it; a step left out is said in the same message. When a script fails and the cause is unknown, a subagent looks at the page's elements and acts; nobody routes around it in silence.

## 2. Designing and changing a skill

1. **Research the whole surface.** The tool's full behaviour, read in its source — how it stores data, its limits, what a round trip changes — with the plugins the user has installed (check the profile's extensions), ending in a real write test. Every external interface and existing tool, searched on the web by research subagents on the session's model, in parallel: reusing one may remove whole parts of the design. All of it before proposing commands or options.
2. **Design top-down.** The stages, the artifacts passed between them and who does each — script, agent or user — designed as a whole and written as a dated spec (root AGENTS.md has the rule).
3. **Review before building**: independent reviewers with distinct lenses — fidelity to the requirements, technical correctness against sources, usability for a fresh agent — on a tight budget, then the advisor.
4. **Stop and think at key points** — research back, design written, review back: is this the best solution, is there a smarter one?
5. **Small fixes the user agreed to** go straight into code and docs, without a spec round, written per §4.

## 3. What a good design looks like

### Shape

- **General and simple, never patched.** Design top-down: one general mechanism solves a whole class of problems at its root, with as few mechanisms as do the job, and the whole is high in quality, elegant and efficient. It pre-builds no machinery for problems nobody has met, and it leaves out none of the basics: what nearly every run meets, and what doing the job right inherently includes, is in from the start. What stays out is defence against problems only imagined. When a run meets a new problem, first ask whether the general mechanism already covers it; if not, re-cut the design at the root so the new case falls inside it. A guard, flag, condition or special case added per issue is patchwork, and patchwork piles up into a skill nobody can follow. General methods win over rules tied to one field, journal or page; a rule that earns its place is stated as a general fact. A redesign is measured by the skill getting shorter and easier to use, not by issues ticked off.
- **Cut where it pays** *(mattpocock: codebase-design, writing-for-agents)*. A module earns its place when deleting it would concentrate complexity, not just move it (the deletion test). A seam is real once two users stand on it; with one it is hypothetical. A separate skill earns its always-loaded description only when it is invoked on its own or another skill must reach it. Each piece of knowledge has one home. Parts that change at different speeds — site hints, definitions, code — sit apart.
- **Remove a step before automating it.** A design that makes a tedious step unnecessary beats one that automates it.
- **A standard where cases share a shape, the rest per case.** Where many cases share a shape (handoffs, briefs, reports), the shared part is defined once and each case fills in its own. A standard earns its place by what every reader finds in the same place and by what it gives the project, not by uniformity; what only some cases need stays theirs.
- **A behaviour the user may want either way is a setting, not a deletion.** When the user turns away from a behaviour already built and tested, it stays behind a switch: a config value holds their standing choice, its default as they chose, and a run overrides it when they ask in the moment. A switch answers a preference the user has voiced; a switch for an imagined preference is the pre-built machinery that *General and simple, never patched* keeps out.

### Facts and tools

- **Facts recorded upstream.** When a later reader has to guess something, find the earliest moment the fact was in hand — not a later step of the same run — and record it there, in a fixed form: a PDF's version on the publisher's page, at download and at the first check, while the page's labels and the clicked link are still there; by save time only the file is left. A smarter guess downstream keeps growing exceptions.
- **Reuse decided by comparison, function by function.** An existing tool is taken where it does the job at least as well as our scripts and agent judgement; ours is kept where it is better, never traded for a worse one because that is reuse. The comparison weighs completeness of information, checkability before a write, control, simplicity, maintenance and risk; a tool left aside gets a technical reason. Licences are no criterion and stay out of comparisons unless the user raises them. The standing example: our metadata agent combines doi.org, Crossref, arXiv, the article page and OpenAlex keywords, finds the published version and previews the item before writing, which beats Zotero's translators, each taking one source and writing directly (the first spec's finding, 2026-09-21 §3.6).
- **Orchestrate, don't absorb.** Skills call each other and other tools' own commands, adding only what those lack plus the task's context. In code too: a script calls the tool's own commands (`opencli browser get`, `find`, `extract`, `wait`, …) and writes only what the tool lacks (in paper-fetch: the PDF finder, the in-page request, the pdf.js viewer), since the tool is updated faster and covers more than a re-implementation. OpenCLI is the adapter layer: adapters are discovered at run time, `opencli browser` is the last fallback, and no skill binds itself to one adapter or CLI detail. A tool's `--help` and skill docs come before writing a helper; where they leave a behaviour open, its source (`gh`) is read rather than guessed or probed blind. Tools are kept current, since an installed version behind its docs breaks the calls.

### The Unix/Linux philosophy

Every command a skill offers is designed, from its first draft, as a Unix/Linux tool: Python inside, Unix outside. Agents already drive such tools without reading their help, and the user prefers working this way *(POSIX 12.2 Utility Syntax Guidelines; Raymond, The Art of Unix Programming; clig.dev; papis and pubs, bibliography tools built this way)*. Where these sources speak of the person at the terminal, that person is the agent as much as the user: one output serves both. This subsection is the one home of these conventions for every skill; a skill's own docs say only what is its own — its words, how its things are named, what each `-` reads.

- **One entry, short words.** Each skill has one entry in `scripts/`, named for the skill and unique across skills (`p2z.py`, `pf.py`). Under it, each command is one English word: a verb for doing (`tag`, `merge`), a noun for listing (`items`, `tags`, as `git tag`). A table in the entry maps each word to its script; `<entry> -h` lists the words, and an unknown word exits 2 with the list. Code in another skill runs the entry by its path.
- **Called through PATH.** A call starts with `set -o pipefail; export PATH="<the skill's absolute path>/scripts:$PATH";` as a statement of its own: every command in the pipeline finds the entry, an upstream failure sets the line's exit status, and the working directory stays the project's.
- **What a command acts on comes after it.** Commands and skills are joined by pipes and files where they can be, a command's output being the next one's input; a script that joins them follows *Orchestrate, don't absorb*. Items, files, records, handoffs and search words are operands, not options (`grep PATTERN`); several search words make one query. Where an operand could name a file or something else, one that looks like a path — holding `/` or ending in a file extension — is a path, and so is every operand of a command that takes only files: a missing one is `file_not_found`, never looked up as something else, and a directory counts as a file. `-` stands for a file whose content comes from stdin — a list (one thing per line: a value, or one of the skill's own JSON lines, read by the field that names the thing), a list of paths, or a document; each command's help says which. A command reads stdin only for `-`. An operand that matches several things lists them all and exits 1; the command picks none.
- **Options by convention.** Short forms, groupable (`-nv`), with GNU long forms beside them, a long one shortened to any unique prefix; options and operands may come in any order, and `--` ends the options. An option takes one value, repeated for more (`--add-tag A --add-tag B`), since an option taking several would swallow the operands after it. A long name means one thing across all skills: `--collection` selects, an option that replaces is `--set-…`, and `--version` only prints the program's version. These letters, each with one meaning, are the only ones used; the conventions check reads this table, one letter per row:

  | Letter | Long form | Meaning |
  |---|---|---|
  | `-h` | `--help` | help |
  | `-n` | `--dry-run` | list what would be done, and do nothing |
  | `-o` | `--output` | where the output goes, stdout when absent; a directory ends in `/` |
  | `-a` | `--all` | include what is normally left out |
  | `-r` | `--recursive` | include what lies below |
  | `-f` | `--force` | force |
  | `-i` | | write in place, as `sed -i` |
  | `-t` | `--to` | the format to convert to, as pandoc |

  `-q`, `-v` and `-V` keep their customary meanings (quiet, verbose, version) and join the table only when a command needs one.
- **stdout is data.** A command that outputs records prints one JSON object per line, each record's status and hint inside it; a command whose product is a document (BibTeX, Markdown, a TSV another command reads) writes it as it is, to stdout or `-o`. stderr carries only what the reader needs and stdout cannot hold: the progress of a run that takes minutes, a warning that bears on the result. When all is done (exit 0), it holds no closing summary and no log of routine steps: the count is `wc -l`, each status in its line. When something is left to act on (exit 1), it ends with a closing summary; when the whole command cannot go on (exit 2), its last line is one JSON object `{code, hint, …}`, the records already done still on stdout and each one left undone there as `not_run`. A search that finds nothing exits 1, as `grep`; an empty listing exits 0, as `ls`. When the reader closes the pipe (`| head`), the command stops printing and finishes its work, its exit status unchanged.
- **Everything is a file.** State, intermediate results, handoffs and configuration are plain files and directories that `ls`, `cat` and `grep` read: configuration under `~/.config/<skill>/`, an environment variable overriding it.
- **Help shaped like a man page.** `-h`/`--help` gives, for each command and subcommand, the usage line under the name the user types (`p2z.py search`), what it does, its options, its exit status and an example or two, without needing the service or the config.

Existing commands are brought over one skill at a time, paper-to-zotero first.

### Code and checks

- **Small, independent, pure-Python scripts.** One function each, coding only the deterministic gaps; the stable interface is the artifacts passed between them, so tools stay replaceable. Skill code, dependencies and tests are Python run by uv, dependencies in the script's PEP 723 block, never a library vendored to dodge one. No other runtime, Node/JS included: a non-Python tool that is best on the merits enters only as an external CLI, like OpenCLI, or not at all, and which of the two is said. A measuring tool in another language for one design study may live in a git-ignored issue reference folder, outside the skill and its tests. Each skill installs on its own: a small helper two skills share is copied into each, its header naming the source and the commit — no shared library.
- **Checks that can fail.** Few strong end-to-end tests at each script's seam, each covering a whole behaviour, with expected values from a source independent of the code *(mattpocock: tdd)*. Every step of a flow ends on a done-when that is checkable, exhaustive and able to fail: it names the observation that would show it false *(mattpocock: to-tickets)*. A process rule an agent would otherwise be told in a sentence becomes a test or lint *(mattpocock: retro)*: a check on our own work, never a matcher for an uncertain branch.
- **Heuristics validated blind.** A heuristic component is explored in stages; after each, it is reviewed and the question asked whether a better approach exists. Before held-out results are seen, the code is frozen and the severity definitions and thresholds are written down with a checksum; it is tested on data it was not tuned on, and a spent test set needs new data. Grading is blind, by subagents, with hidden known-good and known-bad controls, plus your own audit of passed items and your own look at the few items a decision rests on; the graders' raw numbers go beside your tiers. The user sees every option and the recommended one before any code changes.

## 4. Writing for agents

The standard is the writing-for-agents skill *(mattpocock)*: every document follows it, whoever reads it, since what makes a text predictable for an agent makes it readable for the user. Documents here include, but are not limited to: a SKILL.md and its references, a script's `--help` and the messages and log lines it prints, code and config comments, AGENTS.md, CLAUDE.md and the other global instructions, briefs, memory, and what the user reads (README, specs, issues, reports). A design is written by it from the start; when the development is done, the skill is invoked once more for a full pass over everything the work wrote. The agent settles the wording itself, with the advisor's review, and reports the result in brief; instruction text (below) is the exception.

**Constrain what must hold; leave the how to the agent.** Models are capable and keep improving: a document tightens what a delivery requires, an interface other steps rely on, a safety line, a decision the user made, and leaves the steps and the details to the agent's judgement, which does them well. A constraint earns its place by what goes wrong without it; past that point, rules and step-by-step detail cost tokens, can backfire, and restrict the agent's judgement for little gain *(mattpocock: triage, tdd)*. As models improve, old constraints are tested again, and one the model now follows by default is deleted (writing-for-agents: no-ops).

**Words the reader already knows.** Name things with the words the reader uses: a role as main agent, subagent or user (用户), never a word like 人 that could mean any of them; a thing by a plain description, rather than a coined label or metaphor ("two halves") the reader has to decode. A new term, or one you are unsure reads well, goes to the user with what it means before it is used, settled there rather than kept in a glossary (as mattpocock/skills does); until they settle it, the thing is described in plain words.

**Write from the task, not from an old document.** An old document, note, draft or template is a lead for facts, which are then checked; it is never the model for structure, order, wording or argument. The shape comes from the current task, its reader and what they need now.

**Skill text** leaves out what other layers govern (examples simply call the entry's words: `p2z.py search …`). Each external CLI gets one labelled example, plus dated hints of practices established, with run-time discovery authoritative. It holds no personal facts: the repo is public, and root AGENTS.md has the placeholders. Principles like these, and a skill's way of reaching pages, are written into each skill's own prompt, not into the global instructions.

**Language by reader.** What agents read (SKILL.md and its references, AGENTS.md, briefs, memory) is English, quoting the user verbatim in Chinese; what the user reads (README, specs, issues, reports) is Chinese.

**Changing instruction text** — AGENTS.md and `agent-instructions/` — goes through a review loop, however small the change: read it sentence by sentence with a Chinese rendering and name the defect exactly; hunt double readings in every copy the text lands in; write from the user's points in their own words, not from the last draft; fix at the point of use, not with a patch sentence; have the advisor review the draft; show the user one change at a time, **原文** and **修改建议** verbatim with their Chinese, then the reason, and wait. The global instructions change only with the user's consent.

## 5. Deciding with the user

- **Facts are yours, decisions are the user's** *(mattpocock: grilling)*. What the environment can tell is looked up, through a subagent if need be; only decisions go to the user.
- **The user's words are direction.** A suggestion, an example or a passing phrase says where to go; its method is often just the one in view, and its details may be wrong or only partly useful. Before acting, work out the outcome the user actually wants, weigh their method against the evidence and the alternatives, keep what holds, say where you differ and why, then put the options to the user. When a plan looks like a detour, name the more fundamental way first and ask whether its conditions hold; once the user says they do not, or keeps their plan, carry their plan out well.
- **One question at a time, from the frontier.** The decisions form a tree; the frontier is every decision whose prerequisites are settled. Ask one frontier question, wait for the answer, then recompute: a settled decision pushes the frontier outward and unblocks the questions that hung on it, and a question that depends on one still open waits for a later round. (The method is the grilling skill's; grilling asks the whole frontier per round, the user's rule is one question per round.) The work is done when the frontier is empty and the user confirms the shared understanding.
- **Each question in the chat**, never in a dialog tool: the background it needs, the question, options labelled A/B/C (方案 A/B) each with a short example, the recommendation and why. A number or limit you propose is labelled yours.
- **A design is explained by example**, in the turn's final message: the overall idea in a few sentences, one concrete case walked through the flow, then the rough structure — in plain words, without internal vocabulary (§4, *Words the reader already knows*) — and how it stands against these principles: where it follows them, where it departs and why.
- **Decisions are written down as they settle**, in the issue; a proposal stays marked 没拍板 until the user agrees.

## 6. Briefing subagents

- **A subagent's brief is the contract** *(mattpocock: triage)*, written in two places by reader.
  - **The dispatch** sits in the SKILL.md's handoff table and the step that sends; the main agent reads it: the role that takes the work, its model on each harness, how many at once; what each dispatch fills in (the item, the paths of its records, the pass); what comes back and how the main agent checks it; what a resume message carries.
  - **The brief file** is what the subagent reads: the goal; the inputs, by path; the product (what comes back, where, the command or file that records it, the one folder it writes); a done-when it can run and that can fail; the report, of exceptions only; and the rules it cannot read anywhere else: one level deep, no git, what to say when it cannot finish, and for a web role the skill's web lines.
  - The product, the done-when and those rules are always there. What the taker must look at or check before it answers goes in the done-when, which it checks before it ends; the inputs only say what is there. Everything else, what is out of scope included, is said when it applies, and how to do the work is the subagent's.
- **One level deep.** A subagent does the work itself and sends no agents of its own *(mattpocock: research, code-review — their best-documented failure)*.
- **Its report is a hypothesis, not evidence** *(mattpocock: code-review)*: what a decision rests on is checked before anything is built on it.
- **On the web, every agent is the user**: their IP, their Chrome, their institution's login, so a site that sees a crowd blocks the user. Each brief for an agent that touches a site carries the skill's lines for it: work by hand, one request at a time, seconds apart; at most 5 agents on the web at once. A challenge the user can pass goes to the user as a gate; the first other block — a bot check, 403 or 429 — ends that agent's work on that site for the run, reported. The work item waits on that route instead of moving to another: a block is a pause, not a verdict on the route.
- **Writes stay contained.** The brief names the folder the agent writes to, created first; no git add or commit; `git status` once it returns.
- **A redesign stays one design**: the shared interfaces and an exemplar are written first, by the main conversation; then independent modules are ported onto them in parallel.
