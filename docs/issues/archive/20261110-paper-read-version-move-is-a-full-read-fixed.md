# paper-read：把笔记迁到更好的版本，等于把论文重读一遍

> **已解决（2026-11-10）。** 迁移改成先看两版哪里不同、只处理不同之处：paper-read 的 SKILL.md 新增 *Move a note to a better version*；`references/reading.md` 的 *Moving to another version* 改成只写任务（处理两版的不同，且只处理这个），不规定办法；新增 `pr.py diff`，按节或对任意两段文字比较，是可选的现成工具，规则不依赖它。

- 来源：2026-11-10，第一次实际跑换版本（UNSB，`Accepted-arXiv-v3` → `Published-ICLR`）。旁路 agent 的提醒由用户转来：「看一下这个问题」。
- 状态：已解决。

## 经过

- **花了多少。** 读论文的 subagent 用了 35.2 万 token、24.5 分钟、131 次工具调用。两版的文字层逐词相同，只差页边一行 arXiv 戳（主 agent 自己比过）。
- **为什么。** SKILL.md 当时写的是"在新版上通读一遍，就是笔记迁过去的方式"，subagent 照做了：把新 PDF 的包逐页修完，补全旧笔记欠的几问（核心机制、更好的验证、Q9），还读了代码仓库。只有"把笔记指到新 PDF、重新核对 11 处已核对"是迁移本身。
- **照 reading.md 逐段比两份包的 Markdown 也不行。** subagent 报告 39 处不同里 38 处是解析造成的。

## 用户的话（按先后）

- 「如果是排版问题的话，是不是应该按照 Section 去做会好一点？而不是直接全文去比……diff 这一块根据我们的设计原则，实际上是应该交给脚本去做的吧」
- 「如果脚本没法很好地去做，你交给 Agent 让他去分段，然后再按照章节去 diff，也是能提高效率的，而不是让 Agent 去逐字对比。逐字对比的话太原始了，而且效率很低，并且 token 花费的也不值得」
- 「token 要花费在刀刃上」
- 「该脚本做的就交给脚本做，特别是这种重复的逐字对比，没必要 Agent 去做。真的不应该交给脚本做的，你就果断交给 Agent 去做」
- 主 agent 两次把办法写进给 subagent 的规则之后：「Subagent 去调用的时候是不限于工具的，你不要去刻意约束它。只要能完成我们给的任务，或者交接的任务，那就是好的」；「而且万一你写的那个 pr.py diff 不好用呢？」

## 试过的

- **全文逐词比**（写了又撤掉）：能认出 UNSB 这种完全相同的情况，对重排版的版本只给出一个总数和一堆页眉噪音。主 agent 一开始还想让脚本报"相同 / 不同"，那要定门槛，是让脚本替不确定的情况做决定。
- **按节比**（留下的）：在库里 6 对版本上跑过。UNSB 28 节里 21 节相同，其余共差 27 词，全是解析误读或解析时被"改正"的原文笔误。另外 5 对（预印本到期刊正式版）每节都有差别，共差三四千词。

## 还没验证的

- 有真改动时"只处理不同之处"的迁移一次都没跑过；重排版的版本清单仍然很长。
- `pr.py diff` 没在一次真实的迁移里被用过。agent 实际绕开它，或者它的输出帮不上忙，就删掉：规则里只有主 agent 那一步的半句提到它。
