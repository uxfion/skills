# paddleocr：表格比对不把公式拼回去，表头带下标的表都会误报

> **已解决（2026-11-10）。** 原因核实了：正文的检查会先把公式拼成文字层的写法再比，表格比对没有。现在表格比对两种写法都认，复用的是正文检查已有的那一步（`paddleocr/scripts/ocrlib/checks.py`）。
>
> **验证。** 在 25 篇库内论文上（MIRAGE 加 24 篇没参与调试的），新旧代码各渲染一遍：`table_mismatch` 从 16 条降到 6 条，消失的 10 条逐条看过，报的都是下标、上标粘连（`db`、`mr`、`rx`、`ssimtum`），没有新增任何发现。
>
> **试过又撤掉的。** 另加过一条规则：只有上下标的公式并到前一个词上（`SSIM $_{\text{tum}}$` 拼成 `SSIMtum`），能再消 2 条。它是盯着 MIRAGE 剩下的那一条加的，属于往脚本里补规则；多消掉的里面有一条把年份和引用编号粘成了 `199729`，已经超出本意。用户 2026-11-10：「我是怕你会像修补一样，修补得越多越爆炸。有一些通用的东西或者 Agent 能做的东西，那就让 Agent 去做」。撤掉了；剩下的误报由读论文的 subagent 对照页面图像看一眼。
>
> **没做的，和原因：**
> - **丢的 22 个 `∗`、`SSIM_lum` 这两处真错仍然报不出来。** 这项检查按词比对文字层：`∗` 不算词，单独一个词对不上低于"至少两个词"的门槛（门槛是为了不报噪音）。给它们加专门的检查是新的启发式规则，要另外设计和盲测；现在靠读论文的 subagent 用到表里的数字时对照页面图像。哪次再有读论文的 subagent 报丢了显著性标记，就拿出来做。
> - **公式读成乱码没有检查**：同上，没有可靠的办法由脚本判断，留给读的时候看。
> - **库里已有的包**里还留着旧代码算出的误报，下次渲染或读到时自然更新，不专门重跑。

- 来源：2026-11-09 精读那一轮，读论文的 subagent 整理 MIRAGE（`borghesiMIRAGEMultiscaleLesionInformed2026`，arXiv v1）的包时报告。用户没有提。
- 状态：已解决。

## 经过

- **跑的什么。** `ocr.py render` 后包里有 3 条 `table_mismatch`（p4-12 的 Table 1、p6-2 的 Table 2、p6-4 的 Table 3）。subagent 对照 PDF 逐格核对。
- **看到什么。**
  - 3 条报的都是同一件事：文字层把下标和正文粘成一个词（`SSIMtum`、`AUROCC`），包里的表写成公式（`$\mathrm{SSIM}_{tum}$`），两边的词对不上。数字和格子其实都对。
  - 真正的错没被报出来：Table 1 丢了 22 个表示显著性的 `∗`；Table 2 的表头 `SSIM_tum` 被读成了 `SSIM_lum`。subagent 是逐格看图才发现的。
  - 同一篇里 Eq. (2) 读成了乱码（`\cap^{\prime}`），也没有任何检查报出来。
- **原因（subagent 读代码的判断，未核实）。** `paddleocr/scripts/ocrlib/checks.py` 的 table_mismatch（约 466 行）对包里的表分词时没有经过 `glue_math`；正文的检查（`missing_text`、`diff`）是会把公式拼回去再比的。
- **为什么不顺。** 误报让每张带下标的表都要人工逐格核一遍，真正的错反而淹在里面；报的地方和错的地方不是同一处，检查起不到指路的作用。
