- 来源：主 agent · 2026-11-04。出处链接做完，找下一篇要读的论文时，在库里搜 T-CACE 建议接着读的几篇。搜索结果每条都是整个条目，主 agent 想只看"哪几篇、key 是什么"，临时把输出用管道接给 Python 过滤，又把管道接在了 heredoc 脚本前面：数据被丢掉，打出空结果，差点当成"这几篇不在库里"。这个错误是主 agent 的用法问题（heredoc 已经占用了标准输入，不能再接管道），记在它的记忆里，和 skill 无关。
- 用户先问的是：「是我们 Zotero 相关的 skills 里面没有引导好，还是 uv-python 的问题，还是你自己用错了？」然后：「但问题是你这个需求确实是真实的，所以如果能加一个功能，或者优化得好一点，是不是也方便你使用呢？」并提醒这是要去求证的问句，不是结论；又问能不能按 Unix 的思路，用管道接 `grep`、`jq` 这类外部工具；最后指出：「默认搜索能不能拿到比较全的信息呀？因为有时候搜索一次，我可能不会去看里面的摘要什么的，不太可能了解这篇论文」。

## 求证的数据

**谁在用 `--q`。** 仓库里没有脚本用它：`prepare_note.py`、`index_heading.py` 用 `--cite`，organize.md 用 `--collection`、`--cite`，都要整条。`--q` 只有 agent 用，p2z 的 SKILL.md 写的用途是"按标题或作者先找到 key"。

**用得多不多，怎么用。** 数了所有项目会话记录里 agent 实际执行的命令（不算文字里的提及）：

- 70 次搜索，分布在 11 个会话里。61 次在 skills 仓库里（开发和整理库时），真项目里只有 9 次（diffusion、jbhi-revision、hc_deduction）。
- 43 次没接任何工具，直接读完整输出。
- 27 次在后面接了东西过滤：13 次 `head`/`grep`/`cut`/`sed`，8 次 Python，3 次 `jq`，3 次其他。目的几乎都是抠出 key 和标题，或者数条数。

**结果里什么最占地方。** 3 次搜索、246 篇，每篇平均 3 KB：

| 字段 | 每篇 | 占比 |
|---|---|---|
| 摘要 `abstractNote` | 1.5 KB | 52% |
| 完整作者列表 `creators` | 0.5 KB | 17% |
| 标签 `tags` | 0.2 KB | 8% |
| 其余（链接、日期、版本号、ISSN、页码、语言等） | 约 0.7 KB | 约 23% |

## 考虑过的做法

| 做法 | 为什么没选 |
|---|---|
| 搜索默认只打 key、引用键、年份、第一作者、标题 | 每篇只要 0.2 KB，但丢了摘要。搜一次就要判断相不相关时离不开摘要，而 agent 往往不会再单独去查。一开始说的"省 20 倍"只算了找 key 这一种用法 |
| 留下摘要和标签，去掉完整作者列表和记账字段 | 每篇从 3 KB 降到约 2 KB，只省三分之一；要在代码里多一层取字段和测试，搜索在真项目里一共才 9 次 |
| 加 `--brief` 或 `--fields` 参数 | 默认还是整条，agent 不记得加就照旧；记录里大家要的只有 key、标题和条数，用不上这份灵活 |
| 改成纯文本或 TSV | 打破 p2z "标准输出只出 JSON"的约定；JSON 行一样能 `grep` |
| 只靠外部工具（现在的样子） | **就用这个。** 一行一个 JSON 对象本身就是数据流：挑字段接 `jq -r '[.key, .citationKey, .title] \| @tsv'`，按字筛接 `grep`，数条数接 `wc -l`。注意：`jq` 在这台机器上是另装在 `/root/.local/bin` 的，别的机器不一定有；`grep -o '"key": "[A-Z0-9]*"'` 哪里都能用 |

## 重新考虑时

出现下面的情况再看：真项目里搜索变多；搜索结果常常长到要翻好几屏；或者 agent 搜完总要再查一次细节。到时可以先试两条路：

- 去掉记账字段，只留判断一篇论文要用的（标题、第一作者和作者数、年份、出处、类型、标签、DOI、摘要）；
- 摘要只给开头一两句作预览，要全文再用 `--key` 取。
