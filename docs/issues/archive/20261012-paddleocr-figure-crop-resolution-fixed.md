# paddleocr：裁剪图分辨率低

> 已解决（2026-10-12）：新增 `--crop-dpi`，默认 300，可设 72–600。PDF 的裁剪图按这个分辨率从 PDF 重新渲染再切，流水线不动。做法和验证见文末。

## 场景

2026-10-12，用户看完典型图和最差情况的裁剪图后问：「取出来的图片分辨率能控制吗？我看到好像还是不是很清晰，这个能调吗？你去调查一下」。

## 原因

- PDF 每页先渲染成图片，整条流水线都用这张图：版面检测、VL 识别、裁剪。
  - 渲染倍数是 `PADDLE_PDX_PDF_RENDER_SCALE`，默认 2.0，即 144 DPI（`paddlex/utils/flags.py`，在 `image_batch_sampler.py` 里传给 `PDFReader`）。版本 paddleocr 3.7.0、paddlex 3.7.2。
- 两种裁剪图都从这张 144 DPI 的页面图上切：
  - PaddleOCR 自己的单块图 `img_in_*`，`write_page` 只是挪过来；
  - 合成的整图，`parse.py` 的 `save_crop`。
- JPEG 用 cv2 默认质量 95，压缩不是原因。

## 量了多大

典型图那 15 张（见 [20261011 issue](20261011-paddleocr-figures-still-incomplete-fixed.md)）全是 144 DPI：
- 通栏图约 18 cm 宽，裁剪图约 1050 像素宽；
- 半栏到 2/3 栏的图 470–800 像素宽。

图里内嵌的位图，原图分辨率在 212–488 DPI 之间，多数在 300 左右。144 DPI 把它们缩小了 1.5–3.4 倍。矢量图没有上限。

按 300 DPI 从 PDF 重新渲染同一个框，5 张图的对比交给了用户：MINIM Fig. 4、Delphi Fig. 1、MDAgents Fig. 1、LDM Fig. 4、MINIM 扩展图 1。小字、坐标轴、照片细节都明显更清楚，文件约大 3 倍（125 KB → 377 KB）。

## 有没有参数

PaddleOCR 没有只管裁剪图分辨率的参数。唯一相关的是 `PADDLE_PDX_PDF_RENDER_SCALE`，它改的是整条流水线的输入，和 `layout_unclip_ratio` 是同一类（见 [20261011 贴边 issue](20261011-paddleocr-tight-figure-crops-wontfix.md)）：
- 版面模型看到的是另一张图。`page_image` 的说明里记过：渲染方式一变，版面模型给的框就会变。
- 送给 VL 识别的每块区域都变大，识别结果和耗时都会变。变好还是变坏，上游没验证过，见下面 #16815。
- JSON 的 `bbox` 和页面尺寸按新倍数变。`parse.py` 里按 2 倍调过的像素常数也会偏：`FIGURE_MARGIN` 20 px、`LINE_NUMBER_ALIGN` 12 px。

## 相关讨论

- PaddleOCR 讨论 #16815（2025-10-24）「如何提升markdown_images的像素」：
  - 维护者 liuhongen1234567 先答：图是从原始图像裁的，最简单是提高原始图像的像素。
  - 提问者指出 PDF 里是矢量图，应该放大渲染后再裁。维护者答：「pdf的话可以调整读取时候的缩放比例，不过需要修改源码」，即把 `PDFReader` 改成 `zoom=4.0`。又说：「放大后是否会有提升我们并没有进行相关的实验验证」。
  - 现在的版本有了环境变量，不用改源码。
- PaddleOCR #17529（2026-01，已关闭）「識別出來的效果特別差」：PDF 里字小，识别差。
  - 一位用户自己把 PDF 转成高分辨率图片再喂给 PaddleOCR-VL，说准确率大幅提升；维护者答「越高的dpi解析pdf会越清晰，因此识别效果会更好」。
  - 提问者把 VL 的 `minPixels` 往上调时，报了超出 `max_model_len` 16384 的错。
  - 这条说的是识别准确率，不是裁剪图，但说明改渲染倍数会改识别结果。

## 要提高时

不碰 `PADDLE_PDX_PDF_RENDER_SCALE`。在裁剪这一步自己从 PDF 重新渲染：
- 框的像素坐标除以渲染倍数，得到 PDF 里的点坐标；按约 300 DPI 渲染这一页，再裁。
- 两种裁剪图都要换：合成的整图和 PaddleOCR 的单块图 `img_in_*`，只换一种就有一半还是糊的。
- JSON 的 `bbox` 和页面尺寸不动，只换裁剪图文件。
- 不用 GPU，每个有图的页多渲染一次。已有的解析也能这样补，不必重新解析，和 `regroup` 的做法一样。
- 300 DPI 左右就够：位图原图多在 300 左右，再高只是放大像素。
- 只对 PDF 有效。截图、扫描件这类图片输入没有更清楚的来源。
- 和贴边那条的“以后要留边时”是同一处代码，要做时一起考虑。

## 用户决定

用户看了对比后说：「300dpi确实好很多。把他做成可调的吧，默认300dpi，可以设置到600。你的想法和我的思路一样，其他一些流水线上的东西就保持默认，我们尽量不去动它，因为动了可能查问题也不好查。我们就改取出来图的分辨率」。

## 做法

- **参数**：`--crop-dpi N`，默认 300，可设 72–600，超出范围报参数错误。
- **重切**：新增 `recrop`。只处理 `imgs/` 里名字带框的裁剪图 `p<NN>_…_box_<x1>_<y1>_<x2>_<y2>.jpg`，包括 PaddleOCR 的单块图、合成的整图，以及表格里嵌的小图。
  - 这些图在 Markdown 或 JSON 里引用，名字里的框就是当初切的范围。
  - 前面各批测试的解析共 1563 个裁剪文件，有 139 个不被任何块引用：26 个嵌在表格 HTML 里，113 个是 PaddleOCR 存了但没用上的图。所以按文件名来，不按块。
  - 每个有这类图的页，用 PaddleX 的渲染函数 `render_pdf_page_to_numpy` 按 N/72 倍渲染一次。它和流水线是同一个渲染器，也带像素上限，海报页会自动降倍。
  - 按渲染图和 JSON 页面尺寸的比例放大框，裁出后覆盖原文件。文件名、JSON、Markdown 都不变。
- **新解析**：合图之后对整篇重切，在 `parser` 里记 `crop_dpi`。重切出错时保留 144 DPI 的图，不记 `crop_dpi`，stderr 写原因，下次运行再补。
- **已有解析**：跳过时，PDF 解析的 `crop_dpi` 和这次的 `--crop-dpi` 不同，就就地重切。
  - 这包括还没记过 `crop_dpi` 的旧解析，摘要标 `"recropped": true`。
  - 顺序：合图、重切、核对。
  - `crop_dpi` 不放进 `options`，所以改它不会触发 GPU 重新解析；`FORMAT` 不变。
- **不重切**：
  - 图片输入：截图、扫描件没有更清楚的来源；
  - `--photo` 的解析：页面图经过纠偏和矫正，框对不回 PDF。
  - 这两种不记 `crop_dpi`，裁剪图保持流水线切的样子。
- **手裁的图不动**：SKILL.md 让 agent 手裁的图命名为 `p<NN>_fig<number>_cut.png`，名字里没有框。
- **耗时**：MINIM、LDM、Delphi 三篇，300 和 600 DPI 渲染平均每页 0.02–0.09 s，最慢 0.22 s。

改动：
- `parse.py`：`recrop`、`--crop-dpi`、`process()` 接入、文档字符串。
- `SKILL.md`：
  - 第 1 步写明 `recropped`；
  - 第 3 步的手裁改成按 `crop_dpi` 裁：`-r <crop_dpi>`，JSON 的框乘以 crop_dpi/144。
- 测试：
  - 只重切带框的文件，框按比例放大；
  - 跳过时重切一次，再跑不重切；
  - 改了 `--crop-dpi` 再重切；
  - 图片输入不重切；
  - 参数范围。

验证：
- 单元测试；
- 两篇 PDF 用 vLLM 重新解析，裁剪图和对比时 300 DPI 的渲染一致；
- 已有解析就地升级：Markdown 逐字不变，只换图片；
- 600 DPI 跑一篇看耗时和文件大小。

## 实现记录

按上面的做法实现，没有出入。

验证：
- 78 个单元测试通过，其中新增 5 个。
- 新解析，用 vLLM：MINIM 第 4–6 页（`--pages`）、LDM 全篇 12 页。
  - 都记了 `crop_dpi: 300`。
  - LDM Fig. 4 的裁剪图和对比时 300 DPI 的渲染相同，平均差 0.01/255。
  - MINIM Fig. 4 这次的框比上次靠下 2 像素。对齐后平均差 0.5/255，说明 `--pages` 下页码对得上。
- 已有解析就地升级，用 Delphi 的副本，29 页、91 个裁剪：
  - 第一次标 `recropped`；Markdown 逐字不变，JSON 只多了 `crop_dpi`。
  - 同样的 DPI 再跑，不重切；改成 600 重切，再改回 300 又重切。
  - Delphi Fig. 1 重切后和对比时的 300 DPI 渲染相同，平均差 0.08/255。
- 耗时和大小，Delphi 一整篇，含启动：
  - 300 DPI 约 2 s，`imgs/` 从 6.5 MB 变成 19 MB；
  - 600 DPI 约 5 s，49 MB。
