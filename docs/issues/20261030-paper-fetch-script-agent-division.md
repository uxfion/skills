# paper-fetch：脚本和 agent 的分工——脚本判断不了、过不去的地方，没有交给 subagent

2026-10-30 记录。场景：拆分后实测 paper-fetch 经学校登录的那条路（spec `20261030-paper-to-zotero-split-spec.md` §11）。

**跑了什么。** `pf.py fetch --pass 1`，测的是 `he2020mask`（Mask R-CNN，TPAMI，DOI `10.1109/TPAMI.2018.2844175`），没有开放获取链接。

**看到什么。**
- 出版商那条路经学校代理下载到了 IEEE 的正版 PDF，但核对脚本判断不了这么短的题目，给出 `cannot_judge`。fetch 把它当成“错文件”（`wrong_file`）放进 `unverified/`，接着去试图书馆检索系统。
- 在检索系统的访客页停下：`why: sign_in`，`gate: false`。SKILL.md *Get the file* 写着这类停下要交给一个 sonnet 后台浏览器 agent 去点（Sign in → 学校入口），可我既没派，也没说。我自己看了 PDF，手动 `claim --accept`，然后往 Zotero 走了。
- 用户追问后，我先打算让 fetch 脚本自己去点 Sign in，又给短题目加了一条“DOI + 第一作者”的匹配规则。这两样都是在给拿不准的分支写匹配，后来撤回，没有提交（补丁存在 scratchpad 的 `fix1-short-title.patch`）。

**为什么疼。** 出版商有 PDF 时本该在出版商那里就拿下，fetch 却接着去试下一条路；脚本判断不了、过不去的地方，流程没有接到智能的一方。光补这一处不够：脚本和 agent 怎么分工，要从顶层整体设计。

**用户原话（2026-10-30）：**
- 「刚才出版商那上面不是有pdf么。你是测试吧，正常的话，直接出版商那里下载PDF了。如果出版商那里没有的话，那就是走学校的图书馆系统。」
- 「另外，我有一个问题：你学校的图书馆系统，你为什么不能自己点？我记得之前我跟你说过这个问题，你可以自己点的。你查一下有没有相关的文档，或者之前的 skills 里面有写。我记得你上次就碰到过啊，怎么又发生了？」
- 「你可以自己点 login 还有登录，除非是需要我输入账号的这种情况」
- 「我们之前肯定聊过这个事情，而且你已经解决过的，我记得很清楚‘’」「而且你当时还去确认了一下，能否获取到网页上的元素信息，然后通过 opencli browser 自己去点击之类的」「我甚至还记得你写过中间层」
- 「你这种怎么就遗漏了呢？你检查一下其他方面或者其他的点有没有遗漏的。这个疏忽完全不应该的。包括所有的网页，如果你无法通过脚本解决，而且不知道怎么卡的话，先去了解一下页面上的元素，然后进行相关的操作，就自己去点击操作或者其他的一些动作。我当时记得跟你说过，对于这种浏览器的操作，用的是 Sonnet subagent。我们完完全全讨论过的，你为什么就忘记了？什么原因？你好好反思一下，而且我现在很担心你从原来的那个脚本迁移过来的时候，丢了很多东西。真的太不应该了。」
- 「出现问题，如果通过你的脚本解决不了，或者我们之前没有遇到过这种问题，你就应该去派 sub agent 去操作。我们之前有规划好的：脚本是去做那些繁琐的重复工作；对于差异化、不确定的东西，都应该交给 subagent 去完成。这样效率是最高的，而且不用写一大堆的匹配之类的。脚本是重复的工作、可复用的工作，像小手脚架一样。然后 A sub agent 是智能的东西，你可以依赖它。因为它是有自主性的，可以通过自己的探索去实现我们的目标。这个点我们之前也谈过呀。」
- 「你现在也不能修修补补，需要全面的顶层的设计。根据我们刚才说的那些思路。就是脚本和 agent 之间的差异，要合理分工的」
- 「这个点我觉得你应该记到设计思路、设计理念里面了。因为我已经反复提过好多次了」

**已查实的事实。**
- 浏览器 agent 那段流程是原样迁移过来的：旧 SKILL.md 第 126 行 → paper-fetch SKILL.md 第 87 行，后者还点名了“单点登录能过的登录页”。漏掉的是执行，不是文档。
- “`cannot_judge` 当作错文件、接着试下一条路”在拆分前的旧代码里就是这样（旧 `fetch.py` 第 140 行），不是迁移引入的。

**方向（用户定的）。** 脚本只做重复、确定的事；差异化、不确定、没见过的，一律交给 subagent（浏览器操作和小判断用 sonnet）。脚本在把握的边界停下，带着证据交出去，不再加匹配规则。三个 skill 都按这个原则从顶层重新划分工，并且全面查一遍迁移有没有丢东西。

## 实测：图书馆系统这条路交给浏览器 agent（2026-10-31）

- **跑了什么。** 新目录，`identify` Mask R-CNN，启动下载监视器，`fetch --pass 1 --route discovery`。fetch 停在访客结果页（`why: sign_in`，`gate: false`）。照 SKILL.md 派一个 sonnet 后台浏览器 agent 接手，会话 `pf`。
- **它点了什么。** “Sign in” → “Login using:” 对话框里学校那一项（不是 External users）→ 单点登录还有效，直接登上，没有遇到密码页 → 在完整结果里按题目和作者找到这篇的记录 → “Access content in IEEE” → IEEE 经学校代理打开 → “Download PDF” 进入 stamp.jsp 阅读页 → 在页内请求 iframe 里的 PDF，存进下载目录。正式版，TPAMI 第 42 卷第 2 期，386–397 页。
- **看到的问题。**
  - 下载目录监视器没有归位这个文件，记成 `left`（unmatched）：题目太短，核对无法判断，而监视器只认“通过”。主 agent 按浏览器 agent 报告的版本和依据 `claim --accept` 并定了标签。这正是 spec §3.1 要解决的：监视器把拿不准的下载扣下，交给 judge。
  - 在记录页上点 “Access content in IEEE”，链接在会话之外开了一个新标签页。浏览器 agent 改用 `open` 在会话标签页里打开同一网址。
  - Zotero Connector 会把 IEEE 的网址自动重定向到学校代理。
  - stamp.jsp 把 PDF 嵌在 iframe 里，Chrome 不会自己下载。fetch 自己的代码能处理这种页面，浏览器 agent 用了一次同源的页内请求。
- 这三条网站行为要写进 publishers.md，作为带日期的提示，不写学校名。
- **已定 2（2026-10-31）**：派 subagent 以一篇论文为单位。用户先提出：「一篇论文应该由一个 sub agent 去维护。具体来说，它也是一个 OpenCL 的 tab。如果出现问题，你就在上面操作浏览器或者去图书馆检索。也就是说，一篇论文对应一个流程，一个流程对应一个 sub agent。不要派多个 sub agent 去做多个操作。但是我说的也有可能不对，你需要跟我讨论一下。」查了记录：以前定的是“一个 subagent 负责一次完整的尝试”（restructure spec 2026-10-20，用户当时说「对，应该是一个subagent一个完整的try」）。讨论后用户选方案 A：脚本先批量跑；脚本没走完的论文，每篇一个 sonnet paper agent，负责这篇的全部剩余步骤，有自己的标签页；只差定标签的成批交给 judge。并发上限：「A  限流不是很担心，因为我们最多同时跑的时候会有限制嘛，最多是5篇论文同时…应该就最多5个同时跑就好了」。
- **已定 3（2026-10-31）**：一个 agent 碰到拦截时，不做 agent 之间的协调，每个 agent 自己停下、自己报告，这篇在原路线上暂停、不转路线。用户原话：「如果就因为人机验证或者限速等限制，你就直接转头去其他地方查了，那这个查询的记录不就没了吗？这条路径不就直接被你否定掉了吗？」，「我觉得现在应该用方案 3，也就是最简单的方式去实现，后面碰到问题了再说。不要从一开始就把系统做得很复杂，我感觉是没必要的」。

## 第一期验收实测（2026-10-31）

按 SKILL.md 当主 agent 跑，paper agent 和 judge 照 SKILL.md 的模板派（sonnet，后台）。三次都通过，没有碰到验证页，没有推送。

- **Mask R-CNN 走完整一遍。** `fetch --pass 1` 在出版商路线停在学校代理（OCLC）的登录页 → `page` 交接 → paper agent 在自己的会话里打开，单点登录还有效，直接进到 IEEE → `fetch --start` 交回 stamp.jsp → 题目太短，核对拿不准 → `file` 交接 → 同一个 agent 看第 1 页，答 `accept --label Published-IEEE` → 页面交接自动关闭 → 重跑 `fetch` 退出 0。没去图书馆系统。
- **只走图书馆系统。** `fetch --route discovery`：访客视图里就有这篇的 ProQuest 记录，记录页上脚本找不到 PDF → `page` 交接（`no_pdf_link`）→ paper agent 从记录页进到 IEEE（经代理）→ `fetch --start` → `file` 交接 → `accept`，Published-IEEE。这次没用到“点 Sign in”，那一步在上面那次实测里验证过。
- **先有接受稿，再拿正式版（决策 A）。** UNet++（TMI）：先单跑 `--route accepted`，PMC 文章页的 PDF 链接被核对拒了 → `page` 交接 → paper agent 用 `fetch --start --version accepted` 交回同一页，这次拿到 NIH 作者稿（`nihms-1600374.pdf`），核对通过 → `label` 交接 → agent 答 Accepted-PMC → 这篇不算满足（想要正式版）→ 照常跑完整一遍，开放路线经代理拿到 IEEE 正式版 → `label` 交接交给 judge，答 Published-IEEE → 两份并排，`paper_file` 是正式版 → 重跑退出 0。
- **看到的、已处理的：** `outcome.tried` 写的是代理的主机名，已改成网站本身的（`2eb4330`）；`claim --sweep` 没有剩余文件时什么也不打印，已改成最后输出一行摘要。
- **看到的、另记 issue 的：** PMC 的 PDF 链接第一次被拒、一分钟后就拿到了，见 `20261031-paper-fetch-pmc-pdf-first-try-refused.md`。
- **没测到的：** 图书馆系统的“点 Sign in”（这次访客视图就有记录；上一次实测验证过）；“开放链接碰巧是接受稿”这条路（这次用 `--route accepted` 先拿接受稿，测的是决策 A 的机制）；验证页（没碰到，所以推送转达和 10 分钟等待没在实测里跑到）。
