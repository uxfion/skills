# paper-fetch：脚本和 agent 的分工——脚本判断不了、过不去的地方，没有交给 subagent

2026-10-30 记录。场景：拆分后实测 paper-fetch 经学校登录的那条路（spec `20261030-paper-to-zotero-split-spec.md` §11）。

**跑了什么。** `pf.py fetch --pass 1`，测的是 `he2020mask`（Mask R-CNN，TPAMI，DOI `10.1109/TPAMI.2018.2844175`），没有开放获取链接。

**看到什么。**
- 出版商那条路经学校代理下载到了 IEEE 的正版 PDF，但核对脚本判断不了这么短的题目，给出 `cannot_judge`。fetch 把它当成“错文件”（`wrong_file`）放进 `unverified/`，接着去试图书馆检索系统。
- 在检索系统的访客页停下：`why: sign_in`，`gate: false`。SKILL.md *Get the file* 写着这类停下要交给一个 sonnet 后台浏览器 agent 去点（Sign in → 学校入口），可我既没派，也没说。我自己看了 PDF，手动 `claim --accept`，然后往 Zotero 走了。
- 用户追问后，我先打算让 fetch 脚本自己去点 Sign in，又给短题目加了一条“DOI + 第一作者”的匹配规则。这两样都是在给拿不准的分支写匹配，后来撤回，没有提交（补丁存在 scratchpad 的 `fix1-short-title.patch`）。

**为什么疼。** 出版商有 PDF 时本该在出版商那里就拿下，fetch 却接着去试下一条路；脚本判断不了、过不去的地方，流程没有接到智能的一方。光补这一处不够：脚本和 agent 怎么分工，要从顶层整体设计。

**已查实的事实。**
- 浏览器 agent 那段流程是原样迁移过来的：旧 SKILL.md 第 126 行 → paper-fetch SKILL.md 第 87 行，后者还点名了“单点登录能过的登录页”。漏掉的是执行，不是文档。
- “`cannot_judge` 当作错文件、接着试下一条路”在拆分前的旧代码里就是这样（旧 `fetch.py` 第 140 行），不是迁移引入的。

**方向（用户定的）。** 脚本只做重复、确定的事；差异化、不确定、没见过的，一律交给 subagent（浏览器操作和小判断用 sonnet）。脚本在把握的边界停下，带着证据交出去，不再加匹配规则。三个 skill 都按这个原则从顶层重新划分工，并且全面查一遍迁移有没有丢东西。
