# paddleocr：`auto` 不足 8 页时走原生

> 已解决：`auto` 不再看页数。vllm-serve 能提供服务时，每次都用服务；拿不到服务时退回原生，并在 stderr 写明原因。改动见 `paddleocr/scripts/parse.py` 的 `choose_backend` 和 SKILL.md 的 Speed 段。

## 现场

v2 刚推送安装完（`e1d9aa1`）。`--backend auto` 的规则是：总共待解析不到 8 页、且 vllm-serve 的服务没在跑时，走原生后端（每页约 11 秒）。用户问：

> 跟我讲一下，你现在批量解析的策略是小于10页只会单个吗？那小于10页它也会很慢呀，有没有必要全部上VLLM？

> 因为我想着，我们已经费那么大力气去安装了，那为什么不走快速的方案呢？

8 页这个门槛按的是 v2 spec 里估的数（冷启动 50–60 秒、服务每页 1–1.5 秒），偏保守。2026-10-09 实测 2 页截图（RTX 5090 D，按总耗时）：

| 情况 | 总耗时 |
| --- | --- |
| 原生 | 32 秒 |
| vLLM 冷启动（启动服务和加载约 31 秒） | 42 秒 |
| vLLM 服务已在跑 | 11 秒 |

冷启动大约在 3 页时和原生打平。去掉门槛，最坏情况是 1–2 页的冷启动任务比原生慢约 10 秒；之后服务会继续运行 10 分钟，这期间的小任务都只要约 11 秒。代价是哪怕只解析 1 页，服务也会占着约 6.4 GB 显存（32 GB 的 0.2）10 分钟。

## 兼容性

用户追问：

> 我指的就是要考虑兼容性。有些人可能装了这个 skill，但没有装 vLLM，那不就应该调用原生的吗？他们可能也没有 GPU 之类的

去掉门槛只影响已经装了 vLLM 的机器；其余情况都和以前一样，走原生：

- 只装了 paddleocr、没装 vllm-serve：直接走原生，不额外调用任何东西。
- 装了 vllm-serve、没装 vLLM：vllm-serve 回答 `vllm_missing`（约 1 秒），然后走原生。已用一个假的 vllm-serve 实测，2 页 32–40 秒，后端是 native。
- 显存不够（`gpu_busy`）或服务启动失败（`server_failed`，最多等 300 秒）：走原生。
- 没有 GPU：这是 paddleocr 本身的前提（安装说明只给 GPU 版 Paddle）。用 CPU 版 Paddle 理论上也会走原生，但每页要几分钟，没有测过，暂不正式支持。

保持不变：服务在运行中途挂掉时，剩下的文档报 `parse_failed`，不会自动切换到原生。重新运行时已完成的文档会被跳过，只补跑失败的那几份。
