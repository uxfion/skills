- **现场**：
  - 照参考做的页被否了：hc_deduction 的第一版是读完 reports 参考后写的，0 张图、19 张表、正文约 1.6 万字；ceus 那次 Codex 无人值守也读到了组会骨架，做出的页被否。diffusion 那份满意的页，那个会话没读过组会骨架。
  - 满意的页图多字少：hc_deduction 的满意版 23 张图、4 张表、正文约 7500 字；diffusion 23 张图、8 张表、约 1.2 万字。
  - 两份满意的组会页有同一个骨架：
    - 一行说明这一页怎么读，接着一张开场图；
    - 一张"回答一览"表：问题出自哪次会 → 一句话答案 → 第几节 → 状态；
    - 每个问题或主题一节，顺序是：标题（问题加结论）→「答案：」→ 主图 →「怎么看 / 说明什么」→ 支撑图和论文样式的表 → 要组会定的点。
  - zym 技术报告的首屏是"输入 → 本方法 → 输出"一屏，加四张关键数字卡；每节标题是结论，细节折叠起来；总览图从左到右，每一步都用真实图像。
  - 参考里没有"每个问题一张主图""逐条回应上次会议"；"字少、图多、先放主图"只写在对外文档的 *A page for a talk* 下。
  - 做报告的会话读 reports 参考的方式各不一样：有的读全，有的只 grep 标题或关键词。参考有 32 KB，一条命令打印超过约 30 KB 时只回 2 KB 预览。
- **为什么要紧**：照参考做出来的组会页会被否，用户每次开会前都要把同一组话再说一遍。三个项目都纠正了同一组问题，所以毛病在参考本身，不在哪一次没照做。
- **方向**（用户 2026-11-14 定了方向，细节由 main agent 把控：「不用一处一处给我看，这是你的项目，你自己把控……大的方向的变动，或者重要的决策，还是需要来问一下我」；决定见 `docs/decisions/202611.md` D20261114-1）：
  1. reports 参考整份按一套标准重写，不再分"内部报告 / 对外文档"。共同的部分是：
     - 页面回答读者的问题；
     - 第一屏给出全貌；
     - 每节一张主图；
     - 默认骨架（每一部分写明在什么页面上有）；
     - 说法不超过证据；
     - 一个口吻。

     页面的用途（会上对着讲，还是发给人自己读）改的地方，在各条规矩里就地写明：字数和读图说明的写法、展示多少尝试过程、骨架里有哪几部分、载体。
  2. 读参考：每份参考在用到时都读全一次（通用块 *When to read what* 开头那段，rev 2026-11-14）；不再要求每轮修改前重读，压缩后重读靠块里原有那句（D20261114-4）。
  3. 中文组会页的示意图默认用中文、数据图用英文（用户：「1可以」）。页面由脚本拼出来算特例，不保留，"页面手写，图表用脚本"不变。
  4. 发布（推送、重装、各项目同步）等用户点头。改过的参考要在下一次真实的汇报里检验。
