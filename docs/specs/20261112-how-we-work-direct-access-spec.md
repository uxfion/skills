# how-we-work：直接给路径，和发布前检查查出的问题

- **状态**：已冻结（2026-11-12 实现）。用户看过清单后：「可以，你自己向前推进。跟着我们设计原则来。」现在的做法以 skill 本身为准。
- **入口**：读「改什么」。
- **不用读的**：「依据」是三份检查报告的位置。

## 起因

`20261112-how-we-work-reconcile-spec.md` 实现后、发布前，用户要求全部再查一遍：「全部过一遍hww相关所有内容，看有没有问题，还要在演绎一遍所有情况和上升通道，特别是一些低级错误，原则上、设计上、逻辑上的问题」。期间用户指出读参考要先调用 skill 是绕圈：「为什么不直接给路径让他直接读呢？」「我每次装都是同一个位置」「每次调用 skills，它都会把 skills.md 文件直接读进来，也占用了 context」「你不能让 Agent 去改 reference 下面的东西，那是只读的」。

## 改什么

1. **不再绕 skill。** 通用块直接给同步脚本和参考的路径（`~/.agents/skills/how-we-work/`，只读）。skill 的描述只留三种调用时机：接入、改通用规则或对账、到 skills 仓库提 issue。入口文件里和通用块重复的「哪类工作读哪份参考」一表删掉。
2. **两件确定的事交给脚本。** 约定文件缺第一行时 `sync` 直接写上（第一行本来就是脚本的那一块）；`sync` 把项目的路径登记进对账要读的名单（`~/.config/how-we-work/config.json` 的 `projects`，环境变量 `HOW_WE_WORK_CONFIG` 可换成别的文件）。
3. **「规则怎么长出来」重写**：学到的先进记忆并生效；用户又提了一次，或它又一次决定了工作怎么做，就提升进项目文件；用户的原话直接写并说明写在哪，agent 自己总结的先问；是否各项目通用由对账判断。
4. **搬回通用块**：倾向只记成倾向；随口说的数字只表示量级；对比表格式那一句；三个例外（宽调研可派两层 subagent、用户启动的批量任务里不挡下一步的异常攒到最后、用户一个词能答的几点可以编号一起问）。
5. **删掉**「通用块更新后 agent 自己删项目里的条目」。清理重复归对账。
6. **两句读得反的话**：参考和约定文件说法不同时以项目的为准；某类工作要用的事实和那一类的规矩一起放在约定文件里。
7. **对账一节补全**：开始前先读决定记录；项目留在 skills 仓库的 issue 一并接手；做完留一行带日期的记录；写明怎样算做完；发布前把改动对照设计原则过一遍（用户：「你反正提交前最后一遍要在自己做对话这边，用设计原则全部过一下，还有Writing for agent.」）。
8. **小错**：残留的旧说法和旧写法的文件名、指空的引用、读不通的句子、「实验」的触发条件加上「看、问」。

## 有意偏离设计原则的三处（用户定的）

- 约定文件只能按现有参考的名字建（§1 说清单是起点）。
- 通用块写死安装路径（§1 说随机器而变的不写死）。用户的安装位置固定。
- 通用块里写了「北京时间」（§4 说公开的 skill 文字不放个人信息）。

## 推后

各份参考内部自己重复的地方；实验参考和报告参考过大、为一节要读整份。

## 依据

三份检查报告在 how-we-work issue 的参考文件夹 `review-20261112/`：`consistency.md`、`rehearsal.md`、`efficiency.md`。
