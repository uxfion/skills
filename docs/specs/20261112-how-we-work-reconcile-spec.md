# how-we-work：规矩怎么往上升（对账）

- **状态**：已冻结（2026-11-12 实现）。用户：「方向对」，看过简报后：「可以，按照你的建议来」。现在的做法以 skill 本身为准：通用块的 *How a rule grows*、维护参考的 *Reconciling the projects*。
- **入口**：先读「一句话」和「放在哪」，再读「对账」。
- **不用读的**：「为什么改」是背景。

## 一句话

规矩往上升，不再让各项目里的 agent 判断它是不是通用，改成由 skills 仓库的会话定期去各项目看一遍（对账），拿来问用户。

## 为什么改

现在的设计要项目里的 agent 判断一条规矩的适用范围，而它只看得到自己的项目。为了帮它判断，加了「只属于本项目」「待提升」两个小标题、条目末尾的 issue 标记和暂留标记、同步脚本逼着判断。实际结果：两个项目里 88 条进了「只属于本项目」、1 条进了「待提升」；没有任何项目往 skills 仓库提过提升的 issue；通用的规矩被当成项目特有的之后没人再看；规则进了 how-we-work 后各项目的旧版本没人清。用户（2026-11-12）：「现在其实最大的问题是，分来分去，分得有点多了，导致整个有点混乱。什么东西该放在哪里，该怎么提升，怎么区分，都没有讲清楚」。

## 放在哪

只看一个问题：每一轮都用，还是某类工作才用。

| | 每一轮都用 | 某类工作才用 |
|---|---|---|
| 项目 | `AGENTS.md` 块外 | `docs/conventions/<类别>.md` |
| how-we-work | 通用块 | 同名的参考 |

- 刚学到的、只对一个 harness 成立的：记忆。
- 项目的事实（服务器、数据）：项目自己的文档，不上升。
- 设计 skill 的顶层理念：设计原则，它是 how-we-work 的上游。
- 从项目文件往上升不换列：约定文件里的升到同名参考，块外的升到通用块。
- **讲清楚「放在哪、怎么升」的地方只有两处，按读的人分**：项目里的 agent 读通用块的 *How a rule grows*（这张表和第 1 步）；skills 仓库的会话读维护参考里「对账」一节（第 2 步）。别的文件只指过去，不再各说一遍。

## 谁往上送

1. **记忆 → 项目文件**：项目里的 agent。标准是验证过（一再决定工作怎么做，且不管哪个 harness 都成立）。最自然的时刻：正要记一条教训，发现记忆里已经有同样的一条。送上去之后记忆里那条去掉。
2. **项目文件或记忆 → how-we-work**：对账，用户同意。项目里的 agent 不判断「通用不通用」。

用户在项目里只说了一次、但说的是以后都这样的话（「以后图例放右上角」）：当场记进记忆并生效，agent 用一句话告诉用户记在哪、下次对账会带上。对账读记忆，带着用户这类原话的条目直接拿去问他，不必等他再说第二次，也不必先进项目文件。

## 对账

- **谁做**：skills 仓库的会话，只读各项目。
- **什么时候**：用户说一声；发布新版 how-we-work、要去各项目同步时，agent 提出来。
- **读什么**：每个已接入项目的记忆、`AGENTS.md` 块外、约定文件。项目的路径记在本机的 `~/.config/how-we-work/config.json`（`projects`），不进仓库。
- **分量**：主 agent 自己读，默认不派 subagent；两个项目的块外加约定文件一共约 90 条。**只报例外，不出逐条的表**：要问用户的几条、要删的重复、记忆里该进项目文件的。
- **结果四种**：

  | 看到的 | 怎么办 |
  |---|---|
  | 记忆里已经验证过的教训 | 告诉项目的会话，提升进项目文件 |
  | 项目文件里其实通用的规矩（两个项目都有同一条，是最好的证据），以及记忆里用户说成通用的话 | 问用户；同意就进 how-we-work，同时列出各项目里要删的条目 |
  | 项目里和通用规则重复或过时的 | 列出来，让项目删掉 |
  | 确实只属于项目的 | 不动 |

- **用户说「先不管」的**：记在 skills 仓库的 `docs/decisions/`，下次对账不重复问。不在项目文件里打标记。
- **改项目里的文件**：照已有的约定，给用户一段提示词贴到项目的会话；用户说直接去改时，先确认那边没有会话在跑。
- **工作记录**：对账时关于项目的笔记放在 git 忽略的地方；进 `docs/decisions/` 的只有通用的那句规矩和用户的话（这是公开仓库）。
- **不写设计原则**：看到像顶层理念的，照设计原则自己的流程问用户。
- **不等对账的一步**：通用块更新后，项目的 agent 同步时自己查一遍块外有没有和新块重复的，重复的删掉（「块外的优先」这条规矩还在，旧条目会压过新规则）。

## 去掉的

- 约定文件和 `AGENTS.md` 块外的两个小标题（已有的可以留着，不再要求）。
- 条目末尾的 `(issue: …)` 和 `(judged …: stays)` 标记。
- 同步脚本列待提升、有没判过的就以退出码 1 结束。
- 项目为了提升而往 skills 仓库提 issue。项目提 issue 只剩两种：某句通用规则把它带错了；某个 skill 有毛病。

## 保留的

- 约定文件由脚本创建（`hww.py add <类别>`），名字必须是 skill 里的一份参考。
- 约定文件固定的第一行（先读参考），同步时检查文件名和第一行。
- 通用块里明写：先读参考，再读约定文件。
- 项目有意和通用规则不同的，条目里写明是哪条、为什么。

## main agent 自己定的，用户可以推翻

- 项目路径记在 `~/.config/how-we-work/config.json` 的 `projects`。
- 提升后删掉记忆里那条。
- 用户说「先不管」的记在 skills 仓库这边。
- 通用块护栏里去掉「a rule to promote」那半句。
- 接入参考的去向表改一行。

- 对账靠有人发起。
