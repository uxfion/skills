# paper-read：精读做深，从读懂到我们能用的想法（设计草稿）

> **第一期定稿，2026-11-09**，已在 paper-read 实现。来自 issue [20261109-paper-read-reading-for-project-insight.md](../issues/20261109-paper-read-reading-for-project-insight.md)，括号里的"已定 n"指那里的条目。依据：两份调研（issue 参考资料里的 `research-ideation.md`、`research-practice.md`，git 不跟踪），以及 11-06、11-09 两轮共 23 篇精读的实际情况；两篇试读（第 7 节）通过，用户选 A：这些启发和想法会拿去用（已定 17）。

## 1. 要解决什么

用户要精读做到两件事：

1. **读懂、读透**：以后任何任务用到这篇，读笔记就够；机制、前提、证据站不站得住，都清楚。
2. **变成我们能用的东西**：用户的原话是「能吸取什么意见，或者能参考、借鉴的学习的东西，能提供一个思路、比较前沿的概念或者灵感吧，因为有时候一些想法、灵感就是从大量的文献中出来的」，再加上头脑风暴；要深，「真的就是有点类似灵感的，或者说想法的方向的，我们项目中可以用的那些」。

现在的笔记做好了第 1 件的前一半。缺的是：

- **"为什么起作用"和"在哪里会失败"没人问**：Q3 讲方法怎么做，Q6 列前提和局限，但没要求说清核心机制和它依赖的前提，也没要求预测失败场景。调研里，研究者写的读论文指南都问这两件，大模型的读论文提示词几乎都不问。
- **吸收和头脑风暴没有位置**：Q7 只讲论文自己还能往哪走。
- **读论文的 subagent 不知道我们有哪些待解决的问题**：只拿到几个问题。调研的一致结论是：深的启发来自"拿自己卡住的问题去对照每篇论文"（Rota 转述的 Feynman 十二个问题、Hamming 的 10 到 20 个重要问题）；不给这些问题，问"能怎么拓展"只会得到空话（papers.cool 的样例、SciMON 都看到了）。
- **想法到实验之间没有路**：一项研究里，专家把想法真做出来以后，大模型想法的排名反转，暴露的是缺基线、缺消融、太费资源（Si 等 2025）。想法要带着验证方案。

## 2. 整体思路

**精读是一条线**，由同一个读论文的 subagent 在一次精读里按顺序做完：

```
读懂（Q1–Q5） → 读透（Q6–Q8） → 启发与头脑风暴（Q9）
```

**它手里多一样东西：我们待解决的问题。** 第一期由主 agent 写进派读论文的 subagent 的说明，每条一两行，取代现在模板里"项目的问题"那一行。这两轮实测，主 agent 写的两三个带着待解决问题的提问，每篇都足够写出启发。

**笔记可以带方向**（已定 1）：方向性的想法、灵感、可借鉴的东西、头脑风暴，写进笔记，别的项目也用得上；只适合一个项目的取舍和实现细节，放进项目。

**第二期**（先把精读做好，等一个方向积累了几篇笔记再定）：按方向跨论文汇总和头脑风暴；项目里常备的问题清单；想法挑中后做成小实验、结果记回来。

## 3. 一个例子：MIRAGE 对 CEUS 项目

1. 主 agent 取出 MIRAGE，派读论文的 subagent，说明里写进 CEUS 项目待解决的问题（照项目 10-29 的记录），其中一条："无病灶帧上的假增强：模型在无病灶的帧上画出团块；缺对无病灶区域的约束。"（下面几步是试读前写的示意，其中"B 超和 CEUS 帧对不齐"是主 agent 想当然的问题，项目文档里没有；试读的结果见第 7 节。）
2. **读懂**：Q3 的**核心机制**："推理时只有平扫图，病灶增强靠训练时的病灶监督：让输出能被冻结的分割器找到病灶（L_dseg），用分割损失代替要求对齐的像素损失；单加这一类损失，Dice 从 0.495 升到 0.63 左右（Table 1）。依赖的前提：训练时有病灶掩膜；欠增强损失还要求输入和目标同尺度、对齐。"
3. **读透**：答 Q6 前在脑子里照着论文重新实现一遍。Q6 写出**会在什么数据或场景下失败**："输入和目标不同尺度或没对齐时，欠增强损失不成立；评测病例全有肿瘤，无病灶组织里会不会凭空增强没测过。"
4. **Q9 有什么启发**：
   - **可借鉴**："冻结分割器损失：让生成图上的病灶能被现成分割器找到。搬到我们这里的前提是训练时有病灶掩膜，CEUS 项目满足。"
   - **可吸取的**："它评测用的分割器就是训练用的那个，自己评自己；我们评测要换一个不参与训练的分割器。"
   - **前沿概念**：……
   - **和别的论文的联系**：它引用的论文里，库里已有笔记的那几篇，比如同样只在病灶区施加约束的做法。
   - **思路与灵感**："病灶增强不一定要像素对齐的监督，可以改用'下游能不能认出病灶'来监督。CEUS 项目的对齐难题，也许可以绕开，不必硬解。"
   - **头脑风暴**，留下一个想法：
     - **想法**：用冻结分割器损失做 CEUS 项目的病灶监督，替代像素对齐损失。
     - **依据**：MIRAGE Eq. 6、Table 1。
     - **怎么验证**：在现有 CEUS 模型上加这一项损失，训一次，约一天 GPU；和现有模型比；病灶可见度不升，或无病灶帧上出现假病灶，就说明错了。
     - **可能败在哪**：分割器在合成图上不可靠。

## 4. 结构

### 4.1 我们待解决的问题（第一期）

主 agent 派读论文的 subagent 时，把相关方向待解决的问题写进说明，每条一两行，写成"问题：……；原因：……；缺什么：……"。SKILL.md 说明模板里的 `[A project's questions: …]` 那一行改成这些。

### 4.2 笔记的问题

编号不变，只加不删；改动对以后的笔记生效。

| 问 | 改动 |
|---|---|
| Q1、Q2、Q4、Q5、Q7、Q8 | 不变 |
| Q3 | 加一个固定项 **核心机制**：关键的那一步是什么、为什么起作用（作者的理由和消融证据）、依赖哪些前提。用这个领域本来的说法写（已定 2） |
| Q6 | "假设和局限"加：**会在什么数据或场景下失败**（已定 5）；加固定项 **更好的验证**：换你会用什么实验去证明或推翻它的主要结论（已定 10） |
| **Q9（新）** | **有什么启发？** 六个固定项（已定 4）：**可借鉴**（能参考、借鉴的做法：方法、实验设计、评价方式、写法，以及能拿来用的数据集、代码、权重；每条写成方法接口：做什么、什么时候适用、代价多大、效果取决于什么、搬过来要满足什么，前提写到够用就行，不考虑许可证，已定 9、12）、**可吸取的**（它的经验和毛病，我们怎么用上、怎么避开）、**前沿概念**（一句话说清是什么、出自哪）、**和别的论文的联系**（它引用了、库里已有笔记的论文：机制相同、结论相反、能组合；主 agent 知道哪几篇笔记和这次待解决的问题相关时，在说明里点名让它对照，已定 8）、**思路与灵感**（方向层面的启发，不要求马上能做实验）、**头脑风暴**（留下的具体想法，最多 3 个，可以没有；最后一项**没展开的想法**，已定 16）。Q9 开头一段用文字写明对照的是什么工作、哪些待解决的问题，笔记比说明活得久，不用说明里的编号；说明里没有待解决的问题时照实写，各项面向这个领域。另一个项目带着别的问题再读时，并排加它的一段和条目，每条写明对的是哪个问题；只查一处时只写用到的项，其余等整篇精读 |

### 4.3 读的顺序（读论文的 subagent 的说明）

照现在的做法一问一问答，多这几处。这些是读的方法，写给读论文的 subagent，不写进笔记：笔记只放读出来的结果，不写发散了几个、收敛留了几个、草稿在哪、怎么比对的；探索中得到的有意义的内容要留，篇幅不是代价：没展开的想法和原因、查过但排除的线索和理由、查了哪些来源到什么范围（已定 16）。


- **默认带着怀疑读**：大模型审稿偏向正面（调研），站不站得住要靠证据。
- **答 Q6 前**，照着论文在脑子里重新实现一遍，找出没说清的步骤和隐含的前提，再想它会在哪里失败。找到的缺口照旧写成"论文没有说明"。
- **重要的论文查后续引用**（已定 11）：主 agent 在说明里标明这篇是否重要（项目要依赖它做决定、要复现、要拿它对比）；标了的，查几篇直接检验或改进它的后续论文，看结论有没有被推翻或修正，写进 Q6"证据和范围"，标"论文外"、日期和查了哪些来源，上网照现有规矩。标了重要的一次只派一个：几个读论文的 subagent 同时查同一个引用服务，网站看来是同一个人（试读时两个同时查，一个碰上了 429 和限流）。
- **代码按需查**（已定 3）：项目要复现、要拿它对比、要在它上面做，或者论文没写的关键设置只能从代码里找时，才去查；查了写清仓库、日期或版本、哪里和论文不一样，标"论文外"。
- **Q9 放在最后**：顺序是 Q1–Q8、Q9、最后写一句话概括。先读懂、读透，再吸收、发散。思路与灵感、头脑风暴，首先从本篇的核心机制、前提和失败场景出发。"和别的论文的联系"对照主 agent 在说明里给的"库里已有笔记的论文清单"（引用键和标题）找。
- **头脑风暴**：先不加评判、多想几个，这时不看已有的想法，免得被框住；可以试反过来做、从别的领域类比、深挖一个部件、推广、换场景这些角度。再收敛，留下带验证方案的，其余有价值的写进"没展开的想法"；"把方法直接搬过来、什么都不改"不算一个想法。最后和联系到的那几篇笔记里的想法对一下，重复的注明。"和我们待解决的问题无关""没有值得留下的想法"都可以照实写，不硬凑。
- **自查**：照现在的做法，逐条对照出处核对。
- **回报**：现在 reading.md 让"项目的问题"在回报里答、不进笔记；现在说明里写的是待解决的问题，答案写进 Q9。回报里只说 Q9 对上了哪些待解决的问题、哪些还要看别处。

### 4.4 头脑风暴留下的想法

每个写四栏：**想法**（针对哪个待解决的问题）、**依据**（论文哪里，加推断）、**怎么验证**（最小实验、要比的基线、什么结果说明它错了）、**可能败在哪**。

**没展开的想法**（已定 16）：一条一行，写想法、从本文哪里来（论文哪里）、为什么没展开（比如和本文关联弱、缺数据、还没有验证方案、已有人做过）；已经并进别的项、或和已有笔记重复的不列。

"最近的已有工作"等项目真要做之前再查；试过以后结果怎么记，第二期定。

### 4.5 脚本

- `pr.py check --full` 认 Q9 和它的六个固定项、Q3 的核心机制、Q6 的更好的验证（Q5、Q6 原有的固定项就是这样查的）；以前写成的笔记照第 6 节处理。
- 不新增命令。"库里已有笔记的论文清单"由主 agent 用 `p2z.py search --all-fields 论文笔记` 列出来写进说明。

### 4.6 第二期（先留草图）

- **按方向汇总**：同一方向读过几篇后，把这些笔记的 Q9 合起来，跨论文再头脑风暴一次（组合不同论文的机制），可借鉴的做法按它解决的难点归档（彭思达的"挑战—洞见树"），想法去重、合并，标出最值得做的几个，**由用户挑**（调研：大模型给想法排序的可靠度不如人）。
- **问题清单**：每个方向一页，放在项目里（仓库公开，内容不进 skill），写目标、现在的做法、待解决的问题、试过什么。
- **落到项目**：挑中的想法做成小实验，结果记回想法那里；项目的决定照旧记进论文索引。

## 5. 和设计原则的对照

- **分工**（§1）：确定的交给脚本（检查固定项）；读、想、判断交给 subagent；挑哪个想法去做交给用户。
- **知识保持开放**（§1）：头脑风暴的几个角度是起点，读论文的 subagent 可以用别的，回报里说明。
- **事实在最早拿到时记下**（§3）：可借鉴的做法和它的前提在读的当下写下，不等以后重读。
- **约束必须成立的，怎么做留给 agent**（§4）：只把决定深度的几项设成固定项（核心机制、失败场景、Q9 六项）；重新实现一遍、带着怀疑读、代码按需查，写进说明，不设格式。
- **离开的地方**：笔记"只写论文本身"放宽为"别的项目也用得上的都可以写"（已定 1）。改 skill 时，note-format.md 开头"It holds the paper alone"那句要跟着改。
