# how-we-work：项目自己的规则放哪、怎么读、怎么流动

- **状态**：设计中，等用户说可以开始改（九节）。已定的写了决定编号（`docs/decisions/202611.md`）。规则文字的草稿是 `docs/issues/20261117-how-we-work-project-design-rules-not-conventions-reference/draft/rule-text-v6.md`。
- **入口**：一到五节是设计本身，先读。九节是谁定了什么、还等什么。十节是要改的文件。
- **不用读的**：十二节是被放弃的方案和原因，查来历时才读。
- **来源**：三张 issue（`docs/issues/20261117-how-we-work-project-design-rules-not-conventions.md`、`20261123-how-we-work-agents-md-facts-vs-rules.md`、`20261123-how-we-work-agents-md-carries-user-quotes.md`），决定 D20261123-1 到 -6。

## 一、问题和目标

**问题。** 项目 `AGENTS.md` 通用块之外的部分没有尺子，拿不准的都往里放。四个老项目的块外都在 6–10 KB，装着任务定义、结论、命令、状态和用户原话；真正要紧的规则反而被挤掉，network 因此打印过一个密码。项目自己的核心规则（network 的 `docs/guideline.md`、本仓库的 `docs/design-principles.md`）在 how-we-work 里没有位置。现有文字里分法写了三遍（`common.md`、`adopting.md`、`records.md`），三遍不一样。

**目标。** 项目里的每一句话只有一个位置；每个位置是干什么用的讲得清，agent 凭这个就能判断；每轮都在上下文里的只有指针做不到的；用户靠名字找得到；一条规则放的位置不对了，有路可挪。

## 二、一条原则

**一条规则放在它必须被看见的那个时刻会被读到的地方。**

how-we-work 对通用规则已经是这么做的：通用块每轮读，参考到那类活才读，来历要查才读。项目这一半照同一把尺子：

| 什么时候在眼前 | 通用（skill） | 项目 |
|---|---|---|
| 每一轮 | 通用块 | `AGENTS.md` 块外 |
| 到某个时刻 | 参考 | 规则文件 `docs/rules.md`；约定文件 `docs/conventions/<名>.md` |
| 要查才读 | skill 的 issue 和决定 | 项目的记录；出处 `docs/rules-sources.md` |

后面的每一节都是这条原则的展开。出现新情况时，回到这条原则判断。

## 三、三个位置

项目里的文字分两层。**项目内容**讲现在是什么样：代码、配置、数据、spec、结论、README、待办、`docs/goal.md`。**规则**讲以后的活必须怎样。规则有三个位置：

| 位置 | 什么时候在眼前 | 装什么 |
|---|---|---|
| `AGENTS.md` 块外 | 每一轮 | 指针做不到的规则（随时可能碰到、事先没有征兆的；错一次收不回来的）；每个要读的文件一行指针；两三行说明项目是什么 |
| 规则文件 `docs/rules.md` | 设计或改动项目做的东西之前，整份读；做到它某个标题说的那类活之前，读那一节 | 项目做的东西必须怎样、怎么设计、怎么改，按主题分标题；之后是没有参考管的那类活的规则，按活的种类分标题 |
| 约定文件 `docs/conventions/<名>.md` | 做那类活时，跟着同名参考读 | how-we-work 有参考的那类活在这个项目里怎么干，连同干这类活要用的事实 |

- 规则文件接替 `conventions/other.md`，是高优先级的文件（D20261123-5）。`other.md` 的机制都带过来：分标题；开头由脚本写清单；同步时打印标题。
- 默认名 `docs/rules.md`；已有的保留原名（本仓库 `docs/design-principles.md`，network `docs/guideline.md`），它就是那个项目的规则文件，由项目 `AGENTS.md` 块外的一行说明（D20261123-3）。
- 条目只写规则，出处只有一个家 `docs/rules-sources.md`（D20261123-1）。
- 通用块里 3 处出处性质的原话拿掉，搬进一条决定；触发词和示例留着；参考文档里明显多余的原话由 main agent 精简（D20261123-4）。

## 四、放哪：讲清用途和原因，不出判断题

**写法**（D20261123-6）。「一条规则放哪」不写成按顺序问的几道题。几道题的写法改过五轮，每轮都被按字面读出漏洞；共同的原因是把判断写成了流程。改成讲清每个位置是干什么用的、为什么，配成对的例子，判断交给 agent：它知道这条规则是在什么场合被纠正出来的，也就知道它什么时候要用。

**框架用 writing-for-agents 的。** 那个 skill 讲的就是「常驻上下文的文字」和「指针后面的材料」怎么分，这里不另造一套，`project-rules` 参考指过去，只写它在项目里怎么用：

| writing-for-agents 的说法 | 在这里是什么 |
|---|---|
| 常驻上下文的每个词每一轮都要付出（context load） | `AGENTS.md` 块外 |
| 只有部分情况用到的材料放到指针后面（progressive disclosure）；判断的办法是看分支：每条分支都要的才留在上面 | 规则文件和约定文件；「分支」就是这个项目里的各类任务 |
| 指针后面的东西够不够得着，看指针怎么措辞；先把指针写准，写准了还够不着才把内容搬上来 | 通用块里读规则文件的那句是通用说法；项目在块外用自己的话写一行，把时刻放在句首 |
| 环境也是出处，照抄它是一份会过期的副本；只留查不到的 | 命令、目录、架构不进规则，留在代码和 README；只留「没有哪个文件会说的坑」 |
| 沉积：加东西觉得安全、删东西觉得冒险，过期的一层层留下 | 现状（哪台设备跑什么、什么搁着）不进规则；对账就是定期修剪 |
| 说了等于没说的话（no-op） | 通用块、参考、全局指令已经说过的，项目里不再写 |
| 同一个意思只有一个出处 | 一条规则一个位置；出处单放 |
| 相关的东西放在一起（co-location） | 只为解释规则的一小句事实跟着规则；规则文件按主题分标题 |

**规则什么时候直接写在 `AGENTS.md` 块外。** 只有指针做不到的时候，一共两种：

- **随时可能碰到，事先没有征兆。** 不是每个任务都会碰到，而是说不准哪个任务会碰到，所以写不出一个来得及触发、又比规则本身短的条件。例：「配置里有密码，打印任何内容都要遮掉」，随手读一下配置就会碰到。项目改了通用块里随时适用的某条，也属于这一种，因为通用块那条每轮都在：比如通用块说问题记到 `docs/issues/`，这个项目的某类问题记到别处。
- **错一次收不回来。** 指针只要不是每次都灵就不够。例：保存即上线，所以「先改临时副本，检查过再保存」。只算把守这一步的那条；配置内容该怎样的规则不算。这一种不是 writing-for-agents 里的，是 how-we-work 自己的，和通用块里的 *Guardrails* 同一个道理。

每轮都必须知道的事实，写成它带出的那条规则。

除此之外，块外只有两三行项目是什么，和每个要读的文件一行指针。

**规则文件和约定文件之间。** 规则文件装做的东西本身必须怎样（方法能用什么、产品能读什么、配置绝不能怎样）和它怎么设计、怎么改。约定文件装一类活在这里怎么干（在哪些病例上检查、开跑要什么批准、怎么划分数据、文件夹留在哪、报告怎么标注），不管它多么只属于这个项目，因为读它的时刻是做那类活的时候。两者在实验上挨着，用两对例子钉住：

| 约定文件（活怎么干） | 规则文件（东西必须怎样） |
|---|---|
| 每个候选目标在固定病例上看过再报指标 | 训练目标只能来自真实观测 |
| 按病人划分数据 | 预测器不能读基线之后的数据 |

没有参考管的那类活（比如代码怎么写）的规则，放规则文件里、排在后面、用活的种类作标题。

**三个位置都不放的。** 能查到的东西的副本；现状；出处；已经说过的。前两样回它那一类的文件（README、待办、结论、issue、`docs/goal.md`），干某类活每次都要用的事实跟那类活的规则在一起。

拿不准，一句话问用户。

### 做过的检验

这些是定下 D20261123-6 之前做的，留作来历。用户（2026-11-23）指出这类测试说明不了多少：「你平常用 subagent 测也测不出来，因为缺少context，你自己从宏观顶层去把控它」。所以它们只当线索用，写法由 main agent 从整体定。

- **样本**：main agent 读了 ceus、diffusion、hc 约定文件的全部约 80 条和五个项目里六十多条没有参考管的规则。约定文件的条目几乎都只属于那个项目，但都明确挂在一份参考上。
- **盲测两轮**：没看过讨论的 subagent 只凭规则文字分拣真实条目，每轮两个。第一轮（几道题的第一版，44 条）两人 41 条一致；第二轮（第二版，37 条新条目）36 条一致，该进约定文件的没有被吸进规则文件。两轮都报出同一类毛病：题目按字面读会读歪。
- **审阅一次**：一个 subagent 对着决定、现有文件、设计原则和 writing-for-agents 审了一遍，17 条发现逐条核对后采纳（`review/findings.md`）。其中要紧的三条：「每个任务都要吗」放不进安全红线；事实不能一律赶出约定文件；规则文件后半部分的规则要有读它的时刻。

材料在 `docs/issues/20261117-how-we-work-project-design-rules-not-conventions-reference/`：`draft/` 各版文字，`sort-test/`、`sort-test-2/`，`intended/`，`review/`。

## 五、怎么读：两个文件怎么配合

以前是一串：做到哪类活读哪份约定文件，`other.md` 兜底。现在规则文件和约定文件由不同的时刻触发：

- **规则文件**：通用块 *When to read what* 的开头一段加一句通用的：设计或改动项目做的东西之前，整份读规则文件，先于任何参考；做到它某个标题说的那类活之前，读那一节。「项目做的东西」在每个项目里指什么，由项目在 `AGENTS.md` 块外用自己的话写一行，时刻放句首：「设计或改动任一份配置之前，读 `docs/guideline.md`」。同步时照旧打印标题（脚本认的是放了标记的那个文件；别的名字的规则文件没放标记的，不打印）。
- **约定文件**：不变。做那类活时读参考，再读同名约定文件。
- 两个时刻都到了，先读规则文件。同一件事两边说法不同，以规则文件为准；这句话写在规则文件开头。
- **一条规则明明写在文件里却被漏掉**：先把指针那一行写准；写准了还漏，才把它搬到块外。
- **写规则的时刻**：读 skill 的 `project-rules` 参考（接替 `other` 参考）。它放「放哪」的完整说法和例子、条目和出处的格式、规则文件怎么写、怎么挪。

## 六、条目和出处

- **条目**：一条规则一行，先写规则，需要时接一句理由或适用范围，用自己的话。不带日期、原话、决定编号。三个位置同一种写法。
- **出处**：`docs/rules-sources.md`，按规则所在的位置分组，一条出处一行：规则开头几个字、日期、场合、用户原话。决定或 issue 里已有的只写编号。规则挪了，它的出处跟着挪。本仓库已有的 `docs/design-principles-sources.md` 保留原名。
- 这两种格式只写在 `project-rules` 参考里；`records.md` 改成指过去。

## 七、谁做什么

| 谁 | 做什么 |
|---|---|
| 脚本 `hww.py` | 同步通用块；`add rules` 建规则文件；维护规则文件开头两个标记之间的那几行（是什么、什么时候读、有约定文件的那几类活的清单，清单从各参考的开头逐字抄）；别的名字的规则文件里放了这对标记，也照样填；同步时打印规则文件的标题；约定文件开头那一行；发现 `conventions/other.md` 时提示按通用块的分法搬走。脚本不读条目，不判断内容 |
| agent | 判断一条规则放哪；写条目和出处；写准项目自己的那一行指针；挪规则；对账时读各项目 |
| 用户 | 通用块的措辞；`AGENTS.md` 块外和规则文件里的改写、合并、删除；一条规则升成通用；各项目清理时的逐条去向 |

谁能写（只在 *How a rule grows* 写一遍）：用户说过的规则，直接写并告知去了哪；agent 自己想出来的，三个位置都先提给用户（现有规定，不变）。规则文件和 `AGENTS.md` 块外是用户的文件，改写、合并、删除先给用户看；一个例外是对账时删掉通用规则已经说了的条目，那是 `maintaining.md` 现有的做法。

## 八、一条规则怎么流动

每条路都写明由哪个文件的哪句话承担；没有文字承担的路不写进设计。

| 路 | 什么情况 | 谁做 | 由哪里承担 |
|---|---|---|---|
| 记忆 → 项目的三个位置 | 用熟了 | 项目会话 | 通用块 *How a rule grows*（现有，改分法） |
| 在三个位置之间挪 | 它必须被看见的时刻和原来想的不一样；新参考管到了规则文件里的某个标题 | 项目会话；对账时再过一遍 | `project-rules` 参考 *Moving a rule*（新）。挪不改规则，告知一句 |
| 项目 → 通用 | 对账时发现哪个项目都成立 | skills 仓库的会话，用户同意 | `maintaining.md` *Reconciling the projects*（现有；补：规则文件也读；从规则文件来的通用规则，每轮都要的进通用块，有参考管的进那份参考，否则先留着，第二个项目也出现时说明该有一份参考） |
| 通用块 → 参考 | 块里某句只在一个时刻用得上 | skills 仓库的会话，用户同意 | `maintaining.md` 加一句（新）：改通用块时，碰到的每一句先问是不是每轮都要 |
| 通用块或参考 → 删 | 现在的模型不说也这么做 | 同上 | `maintaining.md:20`（现有） |
| 项目 `AGENTS.md` 块外 → 别处 | 指针能做到的，不该直接写在块外 | 接入时；每次发布后对账 | `adopting.md` 验收加一项；`maintaining.md` 对账表加一行（新） |

两处文字不一致时，不设新的优先级链，各在用到的地方说：

- 规则文件和约定文件说法不同：以规则文件为准（写在规则文件开头）。三个位置本不重叠，出现两条讲同一件事，就是有一条放错了或过期了，按四节留一条。约定文件有意偏离参考不算错，写明偏离哪条、为什么（现有）。
- 项目的文字和通用规则：项目的为准（通用块开头，现有）。
- 用户当下的要求和已有规则：动手前先说（通用块 *Who decides what*，现有）；规则要变就先改规则，用户点头，再把东西改过来（`project-rules` 参考 *The rules file*，新）。

## 九、谁定了什么，还等什么

**用户定的**：出处只留 `docs/rules-sources.md`（D20261123-1）；`other.md` 改名成 `docs/rules.md`、它是高优先级的文件（-3、-5）；判断规则写在文件开头（-3）；通用块的出处原话拿掉、参考里多余的原话精简（-4）；「放哪」讲清用途和原因、按 writing-for-agents 来（-6）。

**main agent 定的**（这个仓库的设计归 main agent；用户随时可以改）：

- 新参考叫 `project-rules`。叫 `rules` 会和文件 `docs/rules.md` 撞名，「项目的规则」会指三样东西。
- 实验参考开头那句话加两处：「开跑前的检查和批准」算实验的事；「方法或产品本身必须怎样」归规则文件。
- 新建的规则文件默认英文（agent 读，和约定文件、`AGENTS.md` 一样），改动给用户看时带中文；已有的保留原来的语言。
- 规则文件和 `AGENTS.md` 块外一样是用户的文件：改写、合并、删除先给用户看。
- 直接写在块外的规则只有两种（四节）；「改了通用块的某条」不单列，它是第一种的一个情形。
- `project-rules` 参考里的例子用编的，不用真项目的：这个仓库是公开的，`records.md` 的例子也都是编的。草稿里现在是真项目的例子，写进参考时换掉。
- 不设新的优先级链；不做同名标题的脚本检查（十二节）。

**还等用户的**：

1. 这份 spec 整体：可以开始改了吗。
2. 通用块的措辞：改好后一处一处给用户看原文和改后的。
3. 本仓库的 `docs/design-principles.md` 是用户的尺子，要不要在里面放一对标记让脚本把清单写在开头。不放也能用，只是这一份没有脚本写的开头。
4. 本仓库自己的 `AGENTS.md` 块外有几条只在写 skill 时用（脚本的 shebang 等），该不该挪进设计原则。
5. 各项目清理时的逐条去向表（十一节）。

## 十二、被放弃的方案

- **只改三处文字**：三张 issue 是同一个原因，通用块自己也带原话，只补项目那一半是修补。
- **分界用「这句话换到别的项目还说不说得通」**：约定文件装的本来就是只属于项目的东西，这一问会把它搬空。
- **`other.md` 和规则文件两格并存**：两者定义相同，中间那条线只能靠感觉，样本里落到 `other.md` 的只有一两条。
- **只留 `conventions/other.md`、讲清范围**：装的是项目最核心的规则，叫「其他」名不副实；`conventions/` 是对参考的补充，这一格恰恰没有参考。
- **先问「它约束的是不是项目做的东西本身」**：目录、记录、报告页都是项目做的东西，80 条约定条目里 47 条会被吸进规则文件。
- **把「放哪」写成按顺序问的几道题**：改过五轮，每轮都被按字面读出漏洞，比如「每个任务都要吗」连安全红线都放不进 `AGENTS.md`。共同的原因是把判断写成了流程（D20261123-6）。
- **一条优先级链**（用户的话 ＞ 块外 ＞ 规则文件 ＞ 约定文件 ＞ 参考 ＞ 通用块）：把有意的偏离也当成错，把一次性的要求当成改规则，还把所有参考排到通用块前面；该说的话在用到的地方已经各有一句。
- **脚本检查规则文件里和参考同名的标题**：只对得上最明显的，是为还没出现的问题加的机关。盲测里约定文件的条目没有被吸走。
- **「通用规则退回某个项目」这条路**：没发生过，没有文字承担。
