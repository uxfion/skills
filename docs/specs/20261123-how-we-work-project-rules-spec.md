- **不用读的**：八节是被放弃的方案，查来历时才读。
- **来源**：三张 issue（`docs/issues/archive/20261117-how-we-work-project-design-rules-not-conventions-fixed.md`、`20261123-how-we-work-agents-md-facts-vs-rules-fixed.md`、`20261123-how-we-work-agents-md-carries-user-quotes-fixed.md`）。

## 一、问题

项目 `AGENTS.md` 通用块之外的部分没有尺子，什么都往里放。四个老项目的块外都在 6–10 KB，装着任务定义、结论、命令、状态和用户原话。它每一轮都在上下文里。项目自己的核心规则（network 的 `docs/guideline.md`、本仓库的 `docs/design-principles.md`）在 how-we-work 里没有位置。

## 二、设计

**`AGENTS.md` 只有标题和通用块，块外什么都不放。**（D20261123-8）

项目自己的东西有三个去处：

| 是什么 | 放哪 | 什么时候读 |
|---|---|---|
| how-we-work 有参考的那类活，在这个项目里怎么干（连同干这类活要用的事实） | 约定文件 `docs/conventions/<名>.md` | 做那类活时，跟着同名参考读 |
| 其他规则：项目做的东西必须怎样、怎么设计、怎么改；没有参考管的那类活怎么干 | 规则文件 `docs/rules.md` | 设计或改动项目做的东西之前，整份读；做到它某个标题说的那类活之前，读那一节 |
| 不是规则的：项目是什么、现状、结论、命令、目标 | 项目的文档：README、`docs/goal.md`、待办、结论、issue | 用到时查 |

- 这把尺子和通用规则那一半是同一把：通用块每轮读，参考到时刻才读。项目这一半没有「每轮读」的一层，因为逐条核对过，没有哪条非要每轮都在（D20261123-8 的讨论）。
- 项目和通用块不一样的地方，也放这两个文件：记录放在别处，写在 `conventions/layout.md`；设计归 agent 定，写在 `conventions/with-the-user.md`。每条通用规则起作用的时刻，都有一份参考在那个时刻被读到。
- 规则文件接替 `conventions/other.md`，是高优先级的文件（D20261123-5）：按主题分标题；开头由脚本写清单；同步时打印标题；同一件事它和约定文件说法不同，以它为准。
- 默认名 `docs/rules.md`。已有的保留原名（D20261123-3）；在里面放一对标记，脚本就认它是规则文件，每次同步把它的名字和标题打印出来。
- 条目只写规则，出处只有一个家 `docs/rules-sources.md`（D20261123-1）。
- 通用块里三句出处性质的原话拿掉，记在 D20261123-7；触发词和示例留着；参考文档里明显多余的原话由 main agent 精简（D20261123-4）。
- 通用块 Guardrails 里密钥那一句写宽：读可能带密钥的文件（配置、环境文件）时，值要遮掉。network 那次出事缺的就是这一句，它对每个项目都成立。

## 三、怎么判断

不出判断题，讲清每个去处是干什么用的，判断交给 agent（D20261123-6）。写进文字的只有这几句：

- 讲的是有参考的那类活怎么干，放那一类的约定文件，不管它多么只属于这个项目。
- 做的东西本身必须怎样，不算「活怎么干」，放规则文件，哪怕是做实验时学到的。两对例子钉住这条线：「每个候选在固定样本上看过再报指标」是约定，「训练目标只能来自真实观测」是规则；「按地块划分数据」是约定，「模型不能读拍照之后的记录」是规则。
- 不放进任何规则文件的四样，照 writing-for-agents 的「修剪」和 `/doctor prompt-audit` 的「模型是不是本来就能知道」：能查到的东西的副本（命令、目录、架构）；现状；出处；已经说过的。
- 拿不准，一句话问用户。

完整的说法和例子只写在 skill 的 `project-rules` 参考里（接替 `other` 参考），写规则之前读。例子都是编的。

## 四、谁做什么，规则怎么流动

| 谁 | 做什么 |
|---|---|
| 脚本 `hww.py` | 同步通用块；`add rules` 建规则文件；维护规则文件开头两个标记之间的那几行（是什么、什么时候读、有约定文件的那几类活的清单，从各参考的开头逐字抄）；同步时打印规则文件的名字和标题；约定文件开头那一行，认得旧写法并原地替换；`conventions/other.md` 还在的，提示搬走；**`AGENTS.md` 块外除标题之外还有内容的，每次同步都报出来**。脚本不读条目，不判断内容 |
| agent | 判断一条规则放哪；写条目和出处；挪规则；对账时读各项目 |
| 用户 | 通用块的措辞；规则文件里的改写、合并、删除；一条规则升成通用；各项目清理时的逐条去向 |

- 用户说过的规则，agent 直接写并告知放到了哪；agent 自己想出来的，先提给用户（现有规定）。
- 记忆 → 规则文件或约定文件：用熟了就搬（现有）。
- 规则文件 ↔ 约定文件：新参考管到了规则文件里某个标题，脚本提示，项目会话搬。
- 项目 → 通用：对账时 skills 仓库的会话读各项目的规则文件、约定文件和记忆，哪个项目都成立的提给用户（现有；补上读规则文件）。规则文件里同一类活的标题在两个项目都出现，说明该有一份参考。
- 通用块 → 参考：改通用块时，碰到的每一句先问是不是每轮都要（`maintaining.md` 加一句）。
- 压缩之后，规则文件和参考一样要重读。

## 八、被放弃的方案

- **只改三处文字**：三张 issue 是同一个原因，只补项目那一半是修补。
- **块外留一格，定什么够格进去**（每个任务都要的；随时可能碰到的、收不回来的；固定四样；默认空、有危险或不同才写）：每个判据都只举得出「打印密钥」一个例子，而那一条该进通用块。逐条核对后没有一条非在块外不可（D20261123-8）。
- **块外不放，但留一句「非放不可的先问用户」**：没有符合的例子；那句话每轮都在，本身就在提醒块外可以放东西。真碰到了是规定和实际冲突，冲突本来就要马上告诉用户。
- **分界用「这句话换到别的项目还说不说得通」**：约定文件装的本来就是只属于项目的东西，会被搬空。
- **`other.md` 和规则文件两格并存**，或**只留 `conventions/other.md`**：两者定义相同，中间的线只能靠感觉；装的是项目最核心的规则，叫「其他」名不副实。
- **把「放哪」写成按顺序问的几道题**：改过五轮，每轮都被按字面读出漏洞。
- **一条优先级链**：把有意的偏离也当成错。该说的在用到的地方各有一句。
- **盲测当证据**：两轮盲测和一次审阅做过（材料在 issue 的参考文件夹），用户指出只看文字的 subagent 没有项目里的背景，测不出什么；它们只当线索用。
