# Paper to Zotero

From what the user gives to Zotero items with their PDFs, filed and tagged, and nothing left behind. Two entries: **import** (the steps below; two or more papers, a list, a .bib or search results → read [references/batch.md](references/batch.md) before step 0) and **organize** existing items ([references/organize.md](references/organize.md) instead of the steps). A paper already in the library whose PDF is wanted, to read or parse, needs neither: `uv run scripts/p2z.py read_library pdf --cite <citation key>` (or `--key`; named by title or author, `read_library items --q '<surname title words>'` finds the key first) prints where its PDFs are on disk with their md5, the published version first. Script paths are relative to this file's directory: `cd` there at the start of every shell call. `uv run scripts/p2z.py --help` lists every script with its purpose; each script's `--help` is the reference for its flags, codes and output.

**Identity.** A paper's handle is its **citation key** — Zotero's `citationKey` field, generated by Zotero or Better BibTeX when an item is created, or pinned to the key the user brings (from a .bib, a list, or in conversation: it goes into the record's `citationKey`). Every script that takes `--key <item key>` also takes `--cite <citation key>`; reports lead with the citation key and give the 8-character item key as an aside.

**Authorization.** A request to add a paper is the authorization to write to the library, however politely phrased; a question about what is possible gets an answer, not a write. Changes to existing items are shown as a list first and written on the user's word; scope the user has set once holds for the whole task. The trash (`trash_item.py`) waits for the user's yes to the list its `--dry-run` printed — except an item this run created itself and has to undo.

**The user helps; the work is yours.** The run is the same whether or not the user is watching: you fetch every paper yourself. The user may log in, pass a CAPTCHA or click a download at any moment, and that only speeds things up — the watcher of step 0 files their downloads. Say early what you can foresee needing them for ("3 of these need the institutional login — if you can, log in now: Ctrl+N, a normal window"). Only the last pass of step 3 waits for them.

## Instruments

- `opencli-usage` skill — web access: discover adapters at run time (`opencli list -f json`, filter it). Seen in 2026-09: API-type `arxiv`, `openalex`, `semanticscholar` (429 without a key — one 429 means skip it), `pubmed` (abstract, author keywords, PMID), `dblp`, `openreview`, `hf paper`; browser-type `google-scholar`, `cnki`, `wanfang`. Behind a proxy every call prints a harmless `UNDICI-EHPA` warning on stderr: send stderr to `<work>/scratch/opencli.log`.
- `opencli-browser` skill — the user's real, logged-in Chrome: `browser p2z open / state / click / wait / eval / tab / close`, `web read --url`. Windows open in the background (`--window background`), so the user's focus stays theirs; the last pass opens them in the foreground for the user.
- `pdf` skill — reading a page of a file the check rejected or could not read.
- `papers-cool-search` skill — papers.cool search and venue listings as JSON (steps 1 and 2), one request at a time.

Read [references/publishers.md](references/publishers.md) whenever a publisher page is yours to work (`fetch.py` stopped on it, a discovery system, a click), [references/tagging.md](references/tagging.md) before choosing tags, and [references/install.md](references/install.md) when `ready.py` reports something missing.

## Steps

### 0. Ready

```bash
uv run scripts/ready.py --work <scratchpad>/paper-to-zotero      # else ${TMPDIR:-/tmp}/paper-to-zotero
uv run scripts/claim.py --work <work> --watch --downloads <downloads_dir>     # in the background, the whole run
```

`ready.py` checks Zotero, the write key, poppler and opencli, prepares the work directory (`records/`, `scratch/`, the `.started` marker) and prints the collection tree and `downloads_dir`. Act on what it reports:
- `no_key`: Zotero will show an authorization dialog — tell the user first, ask them to click **Always Allow**, then run again with `--authorize`.
- `config.ask_user`: a setting only the user can give (the library's discovery search page) — ask for it in your first message and add it to the config.
- `no_pdftotext` and other missing pieces: references/install.md.
- `resumed: true`: an earlier run of this task left the work directory — carry on from its records. `leftovers` are reported, never deleted: a PDF that never reached Zotero belongs to the user.

The browser session is `p2z`. Every temporary file of the run lives under the work directory; one-off code goes in `scratch/`.

The **watcher** files every new PDF in Downloads that matches exactly one paper of the run — your downloads and the user's alike, from before the first search to the end of the run. Start it as a background process that lives as long as the run. Where the harness can stream a command's lines to you as events (Claude Code: the Monitor tool), also follow the log, re-armed whenever it expires, so an arrival reaches you between calls:

```bash
tail -n 0 -F <work>/fetch.jsonl | grep --line-buffered -E '"result": "(claimed|left)"'
```

`claimed`: that paper has its file — drop whatever you were doing for it. `left`: a new file matched no paper, or several — look at it. An event never interrupts a running command, so whatever waits looks for the file itself: give every `fetch.py` call `--downloads <downloads_dir>`, and it looks in Downloads and at the records before each paper and while it waits. Where no background process can be kept, that is the only watch.

Done when `ready.py` reports `ok` and the watcher runs.

### 1. Pin the paper

Treat the user's words as a draft: typos, partial titles and loose keywords are normal, so reformulate and search again before concluding anything. Search along the ladder in *Reaching a page*: metadata APIs and API-type adapters first, `google-scholar` and other browser-type adapters next, `opencli browser` last. A journal or conference title is usually pinned in one Crossref call:

```bash
curl -s "https://api.crossref.org/works?query.bibliographic=<title words>&rows=3&select=DOI,title,container-title,issued,author"
```

An arXiv-style title: papers.cool is a fast first stop (`uv run <papers-cool-search dir>/scripts/papers_cool_fetch.py search "<3-6 title words>" --show 5`); its search has no title weighting, carries no DOI and does not index authors, so confirm the title yourself. Several plausible candidates, or none you would stake the library on: show the top few (title, authors, year, venue) and let the user choose.

Done when one paper is pinned by a DOI or arXiv id (failing both, its landing-page URL), every distinguishing word of the request matches it, and no other result fits equally well.

### 2. Draft the record

The paper becomes one JSON record in `<work>/records/<slug>.json` (the citation key when the user gave one, else `<surname><year><first title word>`), which every later script reads and updates in place:

```bash
uv run scripts/doi_to_item.py --doi 10.1109/CVPR.2016.90 --out-dir <work>/records     # --ids FILE (`id<TAB>citekey` lines), --bib FILE
uv run scripts/find_in_library.py -i <work>/records/<slug>.json     # the library → found
uv run scripts/fulltext_links.py -i <work>/records/<slug>.json      # where copies of the paper are → links
uv run scripts/check_item.py -i <work>/records/<slug>.json          # what Zotero will do with the fields → checks
```

**The published version comes first**, unless the user asked for the preprint, and it is settled before anything is created. An arXiv record arrives with `published_candidates` (from arXiv's journal reference and DOI, and a Crossref title search): confirm one against the arXiv comment ("Accepted at ICLR 2024") and the title. None, but the comment or the paper names a venue → papers.cool's venue search or the venue's own listing finds the paper page. Confirmed → `doi_to_item.py --redraft <DOI | paper page URL> -i <record>` turns the record into the published version (slug, citation key, tags and collection kept; the arXiv id moved to `extra`; the old title kept in `alt_titles`), and `find_in_library.py` and `fulltext_links.py` run on it again. `page_unreachable` (the page refuses plain HTTP): read it in the browser and write the fields yourself. No published version found → the preprint is the item, and the report says so.

**What the library already has** (`found`). With a PDF attachment (`contentType` `application/pdf`, an `imported_*` `linkMode`), preprint included: report the citation key and stop — unless the request asks for something the item lacks (the published version when only the preprint is attached, a tidy, a note), which continues at the step that provides it. With no attachment, or only a snapshot or a linked URL: continue from step 3 and attach to that item; a snapshot a new PDF replaces goes into the report's attachments to clean. `near_match` (the title alone, a preprint/published pair, the same title under another DOI) is yours to decide: the same paper → set `found` to `{"key": KEY}`; another paper → add KEY to `distinct_from`; a preprint/published pair is the user's call. `not_found` with `hits > 0` under `qmode: everything` means other items merely mention those words.

**Revise `item`.** A value without a source stays out.
- Item type: a `bookSection` from a proceedings volume is usually a `conferencePaper` (`doi_to_item.py` converts LNCS chapters itself when Crossref names the series). `warnings` naming a possible erratum or correction notice: make sure the DOI is the paper's own.
- Abstract: from `openalex work` / `pubmed search` + `pubmed article <pmid> --full-abstract` (journal articles) / `semanticscholar paper` / `hf paper`, before opening the article page; the page for fields only it has. A PMID goes into `extra` as `PMID: <n>`; Zotero moves it into its own `PMID` field, so a later change sets that field (`update_item.py --set PMID=<n>`).
- Identifier: the item describes the version of record — never where a copy can be downloaded (the file is the attachment, and copies are found again from the DOI):
  - Published with a DOI (IEEE for CVPR/ICCV, Springer for ECCV/MICCAI, ACL's own): that `DOI`, and `url` `https://doi.org/<DOI>`. NeurIPS 2022–2025 (`10.52202`, the printed proceedings' DOI, which leads to their sales page): the `DOI` too, and `url` the paper's NeurIPS page.
  - Published without a DOI (NeurIPS up to 2021, ICML/PMLR, ICLR and TMLR on OpenReview): `url` the venue's own page for the paper — for OpenReview the forum page, not the PDF.
  - Only a preprint: item type `preprint`, `repository` the server, the server's DOI (`10.48550/arXiv.<id>` for arXiv) and its abstract page as `url`, `archiveID` `arXiv:<id>`. Only on OpenReview (rejected, a workshop): the arXiv version if there is one, else a preprint with `repository` OpenReview.
  - Other versions only as identifiers in `extra`: `arXiv: <id>` whenever an arXiv version exists. A conference paper later extended into a journal article is two papers, two items.
- Tags (`[{"tag", "type"}]`): the source's own keywords as type 1 — arXiv categories (`doi_to_item.py` adds them), author keywords from the article page, PubMed or OpenAlex, not MeSH or IEEE index terms — and your curated tags per references/tagging.md as type 0, spelled like the existing tags from `read_library.py tags`.
- No DOI record at all (`no_csl_record`, old papers, pages that ignore content negotiation): *No DOI record* under Rules.

**Destination.** The user named a collection → its key from the tree `ready.py` printed (ambiguous or missing → list candidate paths and ask); several are fine. No collection named → suggest one from the paper's topic and ask, in the same message as any candidate question. No suggestion possible, or nobody to ask → the collection `tmp` (`make_collection.py --name tmp` once if absent) and say so in the report. Put the key (or keys) in the record's `collection`.

Done when the version is settled (redrafted, or the preprint kept for a reason the report will give), `fulltext_links.py` has run on the final identifier, `checks.code` is `ok` (or every flagged item is an accepted mapping), the abstract is filled or confirmed absent, `tags` is written, and the record has a `collection`.

### 3. Get the file: the chain

The **chain** is the order of routes to a paper's full text. One walk down it is a **pass**, and a pass stops at the first route that yields a file:

1. **An open copy of the published version** — `fetch.py --via http --pass N <records>` tries the `links` of version published that a plain client can fetch; one that needs the browser (PMC) goes through `fetch.py --via page --pass N --start <url> <record>`.
2. **The publisher, through the institution's login** — `fetch.py --via page --pass N <records>` opens `https://doi.org/<DOI>` in the `p2z` session and fetches the PDF link the page declares, inside the page and with its cookies.
3. **The discovery system** — `fetch.py --via discovery --pass N <records>` searches the title in the library's discovery system and follows its own "Get PDF" links to an aggregator (ProQuest and the like) through the institution. `not_in_discovery`: no record there carries this title.
4. **The accepted manuscript** — `fetch.py --via http --version accepted --pass N <records>`.
5. **The preprint**, last — `fetch.py --via http --version preprint --pass N <records>`.

An alternate version counts as obtained: its file name carries the version (`<slug>.accepted.pdf`, `<slug>.preprint.pdf`), the attachment title follows it, and the report lists it under alternate versions.

**Scripts first, then you, then the user.** `fetch.py` does the generic thing and never judges a page. When a browser route stops (`{"code": "stopped", "slug", "why", "url", "title"}`), the tab is still on that page and the page is yours. Before each move on it, and before you record a verdict, look whether the paper's file has arrived meanwhile — `records/<slug>.pdf`, `.accepted.pdf`, `.preprint.pdf` or `.html`, those names exactly, or a `claimed` event: it has → rerun the command, which goes on with the next paper. Otherwise work the page as references/publishers.md says — the PDF button, a viewer's bytes, the institutional sign-in entry, a missing subscription, a page nobody can pass; a gate is the user's (*Gate* under Rules). When no file came of it, record your conclusion — `fetch.py --via <the route that stopped> --verdict <result> --pass N <record>` (`no_access`, `no_pdf`, `gate_timeout`, `proxy_unconfigured`, `site_blocked`, `not_public`, …; add `--start <url>` for a page you opened yourself) — then rerun the same `fetch.py` command: it skips what this pass has done and goes on. Purchase pages are never a route.

**Every file goes through `claim.py`**, whoever got it: it checks the file against the paper and files it beside the record (`records/<slug>[.version].pdf`) or moves it to `<work>/unverified/`. A file there that you believe is the paper after all: read its first page (`pdf` skill), move it into `records/` under its version's name, run `check_pdf.py -i` on the record, and set the record's `pdf_accepted` to `{"reason": "…"}`; the report names it.

**Three passes at most.** Every pass is the same chain and may ask the user at a gate. Between passes the items are created and what was found is attached (step 4), so the next pass comes later, when a login, a rate limit or a flaky site may have recovered. The **last pass needs the user**:
1. Finish everything else first. Then report to the user — in the conversation and with a push notification — which papers remain, what each pass met and what each needs. While they are away, each remaining record's `blocker` says what it waits for ("last pass with the user: institutional login"), the report goes out, and these papers resume when the user says "继续".
2. With the user there, walk the chain once more; its browser routes take the papers one at a time in a foreground window (`--window foreground`). At each paper a route stops on, tell the user which paper this is, what the earlier passes met and what they could do (log in, click the PDF button); work the page yourself meanwhile, and wait with `fetch.py --via page --pass 3 --wait --for file <record>` in the background — it ends when the file arrives. The user says 跳过 → stop the wait, `--verdict skipped_by_user`, rerun, and the next paper opens.
3. A paper still without a file gets a snapshot of its article page: `fetch.py --via snapshot --pass 3 <record>`. The page that arrives is checked like any file, so a login page never becomes the snapshot; it is attached like a PDF and listed under 无法获取 with every try, pass by pass.

Done when every record has a file that passed the check (or carries `pdf_accepted`), or its last pass is in `fetch.jsonl` and its snapshot is filed.

### 4. Save and attach

```bash
uv run scripts/check_pdf.py -i <work>/records/<slug>.json       # the filed file against the record → pdf
uv run scripts/create_item.py -i <work>/records/<slug>.json     # one POST: item + collections + tags (+ citationKey) → saved
uv run scripts/attach_file.py -i <work>/records/<slug>.json     # the checked file → saved.key or found.key → attach
```

`create_item.py` looks the paper up once more before it posts: `exists` (a DOI or arXiv hit) writes `found` and creates nothing, and the file goes to that item; `possible_duplicate` waits for your decision, made as in step 2. A failure creates nothing — fix the record and re-run — except `post_incomplete` (the connection broke mid-request): read back with `find_in_library.py --readback` before creating again. `readback_mismatch`: the item exists but a tag or a collection did not stick; `file_and_tag.py --cite …` sets it right. `citation_key_hint`: the key Zotero generated holds a character TeX treats specially (`^`, `_`, `&` …), so `\cite{}` would break on it; ask the user, then `update_item.py --key <key> --set citationKey=<suggested>`.

`attach_file.py` uploads only a file whose check passed with this very md5, or one you accepted (`pdf_accepted`); anything else is `not_verified`. The attachment title follows the file's version (published, `Accepted manuscript`, `Preprint (arXiv)`, `Snapshot`), and its `url` is the canonical page (`item.url`, else `https://doi.org/<DOI>`), never a proxy host. It reuses a half-made attachment and never duplicates a file; if it still fails, hand the file to the user with its path. Both scripts skip what is done (`saved.key`, `attach.md5_ok`), so re-running after a failure is safe.

Done when every record has `saved.key` or `found.key`, and every record with a file has `attach.md5_ok: true`.

### 5. Read back and report

```bash
uv run scripts/find_in_library.py --readback -i <work>/records/*.json && uv run scripts/report.py --work <work> <work>/records/*.json
```

The report comes from the read-back, never from memory. `report.py` prints the table and the sections that apply (无法获取 pass by pass, alternate versions, attachments to clean — the user confirms, then `trash_item.py` — new tags by prefix, leftovers, the pages `fetch.py` stopped at with your verdicts). Add to it:
- `zotero://select/library/items/<key>` links, and the collection path (in `tmp`: ask the user to file it later);
- substitutions — a file accepted on your own reading, an item built through the recognizer, fields left empty for lack of a source, fields `check_item.py` said would be mapped or moved to Extra, fields set against a source other than the DOI record, with that source named;
- the gates hit, the hosts left alone, the sources a 429 stopped, and the residue in one line;
- **skill notes** — anything this skill lacked, got wrong or made you work around (a site that behaved unlike publishers.md says), for the user to decide whether to change it.

### 6. Clear residue

```bash
uv run scripts/claim.py --work <work> --sweep --downloads <downloads_dir>
```

**Residue** is the work directory (records, files, `inbox/`, `stray/`, `unverified/`, `fetch.jsonl`, `scratch/`), the `p2z` session, the watcher, and anything in Downloads newer than `.started`. Stop the watcher. `--sweep` lists the files newer than `.started` still in Downloads, each marked `in_library`: delete those this run downloaded that the library holds, and name the rest in the report (a file the user downloaded for themselves is theirs). Then delete the work directory — Zotero holds its own copy of every attached file — and close the `p2z` session. Delete only what this run created, and a file only after its `md5_ok: true`: a file that did not reach Zotero is a deliverable, handed over with its path. Every exit path ends here; a wait for the user is a pause, not an exit — a record with a `blocker` keeps the tab, the session and the work directory until the run resumes or the user drops it.

Done when the Downloads folder holds no file of this run, the work directory is gone, `opencli browser p2z close` has answered "tab lease released", and anything you could not remove is named in the report with its location.

## Rules

### Reaching a page

Fall back instead of stopping: a blocked request, a verification page or an empty result is a reason to take the next rung.

1. Direct access — metadata APIs (doi.org, Crossref, OpenAlex, arXiv), web fetch.
2. OpenCLI adapters, discovered at run time. An API-type adapter (`browser: false`) is still a direct request and fails the same way when blocked; when it does, `opencli web read --url …` reads the page inside the user's Chrome with their cookies, and `opencli browser` lets you work the page yourself.
3. A browser-type adapter (`browser: true`) that fails was already in the real browser, so it was most likely blocked: open the same page in the `p2z` session and look — a verification or login page is a gate; a normal page means the adapter broke, so read it yourself. Keep the adapter's raw output in `scratch/` for the skill notes.

Retry a transient error once; a 403 or a verification page goes straight to the next rung. Publisher hosts and Google Scholar start at rung 2; Google Scholar at most once a minute. A host that answers 429 is done for this run (the scripts stop it themselves). Files a tool writes on the way go into the work directory and leave with it.

### Gate

A gate is anything the user can pass and you cannot: institutional login, CAPTCHA ("Are you a robot?", "verify you are human"), a cookie wall, an authorization prompt, a purchase page whose institutional sign-in you have already clicked, Chrome or the OpenCLI extension not running, a Save As dialog, Zotero's authorization dialog. Recognise a gate by its markers: page title "请稍候…" / "Just a moment…" / "Are you a robot?", `input[name=cf-turnstile-response]`, `#captcha-box`, a login form, "Get access". Read `state` (URL and title) after **every** navigation or click on a publisher site, because a gate is an unexpected page, not an error. The moment a marker shows, alert first — before any further `wait` or `state`, even when the widget says it has verified and is waiting — then watch it; it may pass by itself, and the alert cost nothing.

Wait at a gate once per pass. **Alert the user** with a push notification (load the tool if it is deferred) — and, when you are a subagent, a `SendMessage` to the main conversation with the same line, since only the main conversation reaches the user's screen. Say which page waits and what to do; for a login, "Ctrl+N for a normal window and log in there": the login holds for the whole of Chrome, so the gate tab stays untouched. *Then* wait up to 5 minutes, reading the page only:

```bash
uv run scripts/fetch.py --via page --pass N --wait --downloads <downloads_dir> <record>   # --until "Access provided by": text or selector only the passed gate shows
```

It looks at the tab and at the paper's file every 10 seconds and ends on whichever comes first:
- `arrived` — the file came another way (the user downloaded it): go on with the next paper. The gate itself was not passed, so the next paper behind it may wait afresh.
- `passed` — the page shows `--until`, or, without it, its URL or title changed: continue where you stopped.
- `gate_timeout` after 5 minutes, logged as this pass's try for the paper: leave the gate tab as it is, open a new tab for what follows (`opencli browser p2z tab new`, then `tab select` it), and take the paper's next route. For the rest of the pass, other papers behind the same gate go straight to their next route (`--verdict gate_timeout`); the next pass meets the gate afresh.

A login from another window leaves the gate tab as it was, so the user's word ("登好了") is what ends that wait: run it in the background where the harness tells you when a command ends, so their reply reaches you meanwhile, and stop it when the reply comes; in the foreground, give the command a timeout above 300 s. Record every gate you hit (page, time, what you were doing) for the report.

Pages nobody can pass — the proxy's "Host Needed", a site's block page — are not gates: tell the user at once, record the verdict, and leave that host alone for the rest of the run (references/publishers.md, *Pages nobody can pass*). A missing subscription concerns one paper; the next paper on the same site is tried as usual.

### No DOI record

`doi_to_item.py` reports `no_csl_record`, or the paper has no identifier, but the PDF is in hand: let Zotero's recognizer identify it. Note the library version (`Last-Modified-Version` of `GET /api/users/0/items?limit=1`), send the PDF through the connector — one request, no key:

```bash
curl -s -X POST http://127.0.0.1:23119/connector/saveStandaloneAttachment \
  -H "Content-Type: application/pdf" -H "X-Metadata: {\"sessionID\":\"$(uuidgen)\",\"title\":\"paper.pdf\",\"url\":\"<source url>\"}" \
  --data-binary @<work>/records/<slug>.pdf
```

Within a minute a parent item appears (`GET /api/users/0/items?since=<version>`); put its key into the record's `saved`, revise it with `update_item.py` and finish with `file_and_tag.py` (it landed in whatever collection Zotero had selected). No parent after a minute: move the standalone attachment to the trash (`trash_item.py --key`) and write the record's `item` by hand (`check_item.py --help` prints a skeleton), then steps 4–6 as usual.

## Limits

- `attach_file.py` names the file itself (Zotero does not rename API uploads); the user can "Rename File from Parent Metadata" in Zotero at any time.
- Zotero's PDF recognizer runs only for files sent through the connector, never for local-API uploads.
- Out of scope, handed citation keys instead: finding papers by topic (`papers-cool-search`, OpenCLI adapters), reading a paper's body, editing a manuscript.
