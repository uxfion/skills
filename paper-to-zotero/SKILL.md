# Paper to Zotero

Everything in Zotero: items with their PDFs, filed and tagged; the library tidied, fixed and exported; the notes and structured packages kept beside the papers. This skill never goes online: finding a paper and its PDF is the paper-fetch skill's, reading one through is paper-read's. Script paths are relative to this file's directory: `cd` there at the start of every shell call. `uv run scripts/p2z.py --help` lists every command with its purpose; each command's `--help` is the reference for its flags, codes and output.

| operation | where |
|---|---|
| Import papers: a title, DOI, arXiv id, link, list, .bib or search results | [references/import.md](references/import.md) |
| A library paper's structured package and PDF, to read or parse | *Reading a library paper* below |
| Tidy or fix the library: tags, collections, fields, duplicates, attachment titles, the trash | [references/organize.md](references/organize.md) |
| A note: take it out as Markdown, put it back | references/organize.md, *Notes* |
| Export a collection as BibTeX | references/organize.md, *Exporting BibTeX* |

**Sibling skills.** Each is installed on its own, beside this one; an operation that needs one checks for its `SKILL.md` when the operation starts:

| operation | needs | missing → |
|---|---|---|
| Import | paper-fetch (`../paper-fetch/`): identifies papers, gets and labels their files | stop before step 0; tell the user to install paper-fetch |
| Import, or reading a library paper, when a PDF has no structured package | paddleocr (`../paddleocr/`): parses the PDF | the PDF is archived without its package: name it, and tell the user the skill to install |
| Organize: renaming attachments by version; looking a missing DOI up | paper-fetch | those two wait; the rest of the tidy goes on — tell the user to install paper-fetch |
| Reading a library paper: what it says, its note | paper-read (`../paper-read/`) | read the package yourself, the PDF the authority on every number; tell the user the skill to install |
| Notes, export, fields, tags, collections, duplicates, the trash | none | — |

**Identity.** A paper's handle is its **citation key** — Zotero's `citationKey` field, generated by Zotero or Better BibTeX when an item is created, or pinned to the key the user brings (from a .bib, a list, or in conversation). Every command that acts on library items takes `--cite <citation key>` beside `--key <item key>` (an attachment has only its key); reports lead with the citation key and give the 8-character item key as an aside. Asking the user to find something in Zotero, name it as their window shows it: its title, its collection's path.

**Authorization.** A request to add a paper is the authorization to write to the library, however politely phrased; a question about what is possible gets an answer, not a write. Changes to existing items — fields, tags, collections, merges, the trash — are shown as their `--dry-run` list first and written on the user's word; an item this run created itself and has to undo needs no word. Scope the user has set once holds for the whole task.

**Read back.** What a task wrote is read back from the library as it is now — an import's report, a tidy's second lint — never from memory.

**The scratch directory.** Whatever a task writes outside Zotero lives in `<scratch>`: the session's scratchpad, else `${TMPDIR:-/tmp}`, never a project's folder. An import works in `<scratch>/paper-to-zotero/` (`<imp>` below and in references/import.md); a package taken out unzips to `<scratch>/<cite>.<title>/`, its note file beside it. The task ends by deleting what it created there once Zotero holds it; a file that did not reach Zotero is the user's, handed over with its full path.

## Handoffs

A script settles only what is certain — an identifier that matches, the same md5, Zotero's own reply — and stops at everything else with its evidence. The table indexes those stops and the work beside them; the step it points to sends each, and the brief is what the taker reads.

**Judges and tagging subagents** are background subagents on a cheap model (Claude Code `model: "sonnet"`, Codex `luna`), about 20 cases each, up to 10 at once, judges and tagging subagents together, since they touch no site. A judge reads only the files its brief names, and may run the recording command's `--dry-run`; what it cannot settle it answers `unknown`, and the step says who takes that. Each is sent with its brief and what the step fills in; a role that writes files gets `<n>`, a number of yours unique in the run, so no two write the same file:

```text
You are a paper-to-zotero <role>. Your brief: <paper-to-zotero's directory>/references/<brief>. Run its commands from
<paper-to-zotero's directory>. <imp> (or <scratch>) is <path>[; <n> is <n>]. Yours: <the cases the step names>.
```

What comes back is checked against the files before anything is built on it; a case still open goes into the next batch, or to you. Without subagents, do the work yourself by the same brief.

| stop | taker | brief | what comes back, recorded by |
|---|---|---|---|
| `same_paper` handoffs in `<imp>/handoffs/` (`prepare`'s `decide`, `waiting_on: judge`; `save`'s `possible_duplicate`) | same-paper judges | references/same-paper-judge.md, sent from references/import.md, step 3 | an answer per candidate, in the handoff: `p2z.py answer <handoff> same\|distinct\|pair\|unknown --key K --by judge` |
| a `pair` or `unknown` (`waiting_on: user`) | the user, in the run's one message of questions | references/import.md, step 3 | `p2z.py answer <handoff> same\|distinct --key K --by user` |
| `tags` (`prepare`'s `decide`; `save`'s `untagged`) | tagging subagents, or you for a few papers | references/tagging.md, sent from references/import.md, step 3 | a tags file per paper, `<imp>/tags/<slug>.json`, which `save` writes into the new item |
| `published_versions`, `checks`, `warnings`, `unanswered` (`prepare`'s `decide`) | you | references/import.md, step 3 | the record: a redraft or `keep_preprint`, the item or `accepted`; `prepare` again |
| a stub's PDF (`attach_file` answers `unchecked`) | `p2z.py recognize`, then recognizer judges | references/recognizer-judge.md, sent from references/no-doi-record.md | `verdicts.<n>.jsonl` and `changes.<n>.jsonl` in `<imp>/recognize/`; you write the changes with `update_item --batch`, then file and tag the item; nothing recognized: the item written by hand |
| lint's findings in a tidy | tidy judges | references/tidy-judge.md, sent from references/organize.md, *A tidy*, step 3 | `verdicts.<n>.jsonl`, `changes.<n>.jsonl` and `tags.<n>.jsonl` in `<scratch>/tidy/`; the changes written on the user's word by `update_item --batch` and `file_and_tag --batch` |
| tags in a tidy | tagging subagents | references/tagging.md, sent from references/organize.md, *Tidying tags and collections* | `<scratch>/tidy/tags.<n>.jsonl`, written on the user's word by `file_and_tag --batch` |
| merges, the trash, renames of existing items | the user | the `--dry-run` list | the same command without `--dry-run` |

## Reading a library paper

Every PDF in the library has a **structured package** beside it: a zip under the PDF's title, holding the paddleocr skill's parse of that PDF (the Markdown, its record, the figures). Outside Zotero it is named `<citation key>.<title>` (`zhuUnpairedImagetoImageTranslation2017.Published-CVF.zip`), so the file alone says which paper it is. Read a paper from its package:

```bash
uv run scripts/p2z.py structured take --cite <citation key> -o <scratch>
```

`--key` names the item by its key; named by title or author, `read_library items --q '<surname title words>'` finds the key first. `take` picks the best version; `--title <attachment title>` picks another (`read_library pdf --cite …` lists them, best first, with each file's path). Reading the package — and the paper's note before it, where what the paper says is already answered — is the paper-read skill's (*Look it up*, *Read a paper*). Then:

- `package: null` (the PDF came in where there was no GPU): parse `input`, the link `take` made, with the paddleocr skill (*Sibling skills*), `-o <scratch>`; a parse beyond fixing in place: the same with `--force`;
- after a parse, a settled finding or a fix: `uv run scripts/p2z.py structured put <scratch>/<cite>.<title>/`, so the next reader gets your work (an unchanged folder is skipped).

Done when every folder you changed is put back.

## Limits

- `attach_file` names the file itself (Zotero does not rename API uploads), as Zotero's default template would in English: `<first creator, et al. / and> - <year> - <title cut at 100>`. Zotero renames it later when the item's details change.
- Zotero's PDF recognizer runs only for files sent through the connector, never for local-API uploads (`recognize.py` uses it on purpose).
- Out of scope, handed citation keys instead: finding papers by topic (`papers-cool-search`, OpenCLI adapters), fetching a paper or checking its file (paper-fetch), reading a paper through and writing its notes (paper-read), editing a manuscript.
